## 2. 请求与隐私边界

请求实现遵循以下约束：

- 请求路径固定为逐段构造的 `/responses`，鉴权只通过 Secret Store 引用注入 Bearer header；
- 提示层级不扁平化：应用硬规则为 `system`，阶段契约、故事资料和运行记忆为 `developer`，本次用户要求为 `user`；
- 每个生成请求显式发送 `store:false`；
- 不发送 `conversation` 或 `previous_response_id`，长篇小说的状态只认织卷本地数据库；
- 结构化输出使用 `text.format` 下的严格 `json_schema`；
- 请求正文由可清零 UTF-8 byte buffer 构造，不建立包含整段提示的普通请求 body 字符串；
- Responses 创建协议未定义的 `seed` 和幂等键在联网前拒绝；
- `temperature`、`top_p`、`reasoning.effort` 和结构化输出属于模型相关能力，默认 `UNKNOWN`，只有后续能力登记/探测明确支持才允许发送；不根据模型名称猜测。

最后一项来自二次代码评审：API 接受某个字段，不等于任意模型都支持它。默认失败关闭可以避免一次无意义的付费失败请求，并为 TASK-027 的模型能力登记器保留明确注入口。

## 3. 流式终态规则

Responses 与 Chat Completions 的终止语义已严格隔离：

| 服务端事件 | 织卷结果 |
|---|---|
| `response.completed` | `Completed(STOP)` |
| `response.incomplete` + `max_output_tokens` | `Completed(LENGTH)` |
| `response.incomplete` + `content_filter` | `Refused(SAFETY)` |
| `response.failed` | 标准 `Failed` |
| `error` | 按结构化 code/type 映射 |
| EOF 前没有上述终态 | `STREAM_INTERRUPTED` |

Responses 不等待 `[DONE]`。正文来自 `response.output_text.delta/done`，拒绝来自 `response.refusal.delta/done`。官方允许未来新增事件类型，因此未知非终态会忽略；但未知终态不会被猜成成功，最终仍失败关闭。

如果事件带 `sequence_number`，必须严格递增。重复或倒序事件会产生 `PROTOCOL_MISMATCH`，不会把同一段正文写两遍。usage 在唯一终态前发出，覆盖输入、输出、缓存读取、缓存写入、推理和总 token。
