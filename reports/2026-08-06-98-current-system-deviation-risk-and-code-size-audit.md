## 1. 给不懂开发的人看的结论

织卷现在不是“代码没写”，而是“发动机零件做了很多，整车还没有装起来”。

- 数据库、加密、模型协议、流式草稿、状态机、章节记忆、连续性检查和原子提交等底层已经有大量代码与测试。
- 用户当前能实际操作的 App 只到：首次说明 → 配置 API → 管理连接 → 填写小说设定 → 本地保存 → 查看费用未知的确认页。
- 点击确认后不会开始生成。正式界面明确显示：`生成执行器尚未接入，当前没有调用模型。`
- 已保存的书没有书架入口，用户也没有阅读器、目录、模板复制、手动备份或恢复入口。
- 当前没有发现用户能够直接触发的 P0 级密钥泄露、正文覆盖或无限扣费漏洞；主要原因之一是小说生成主流程尚不可达，而不是所有风险都已解决。
- 当前最可能造成真实损失的不是黑客攻击，而是开发现场没有 Git 存档和远程副本：134 个未跟踪文件与 51 个已跟踪改动文件只存在于本机工作目录。

综合判断：

| 使用方式 | 当前结论 |
|---|---|
| 继续本地开发 | 可以 |
| 测试连接和创建页 | 可以；完整连接验证会在明确确认后发送最多 16 tokens 的小请求 |
| 自动生成一章或整本小说 | 不可以；总 runner 不存在，UI 没有启动入口 |
| 阅读已经保存的书 | 不可以；没有书架和阅读器入口 |
| 复制上一本书的模板重开 | 不可以；只有数据库底座，没有产品流程和 UI |
| 把它作为唯一写作工具 | 不可以；没有可用的备份恢复和内容访问闭环 |
| 发布或长期安装使用 | 不可以；关键 P0 产品能力、签名、实机和真实 Provider 验收未完成 |

## 4. 已确认的重大问题

### P1-01：当前开发成果没有可恢复的 Git 存档

傻瓜式解释：现在这些成果像只保存在一台电脑桌面上的唯一文档，没有“保存版本”，也没有网盘副本。

精确检查结果：

- 分支：`main`。
- HEAD：`8ce774429da1c3f7139a221bc241c34d81a2efdd`。
- Git remote：0。
- `git status --porcelain=v1 -uall`：185 个文件级变更入口。
- 其中已跟踪改动：51 个文件。
- 未跟踪文件：134 个。
- 仅已跟踪差异已有约 `+6,835 / -268` 行，未跟踪文件还没有包含在这个 diff 数字中。

影响：本机磁盘、目录误操作或恶意软件出问题时，TASK-059、TASK-060、TASK-061 和大量报告无法从 Git 恢复；测试结果也无法绑定到不可变提交。

处理要求：在继续扩大 WIP 前，先做安全扫描，再按可审查阶段形成 Git 提交；远程地址只能使用用户指定的私有仓库，不能擅自添加。

### P1-02：最关键的“总 runner”没有实现，甚至没有独立任务编号

傻瓜式解释：每个车间都造出了一些零件，但任务清单里没有一项明确负责“把整台机器接起来并让它自动运行”。

证据：

- `ZhijuanApp.kt:216` 明确显示生成执行器尚未接入。
- `GenerationForegroundService.requestStart` 在正式 `src/main` 中没有调用方。
- `ChapterFinalCandidateCommitStageExecutorV1` 注释明确是给未来 total runner 使用。
- `app/src/main` 没有调用各生成 Coordinator 的生产代码。
- 文档多次写“总 runner 留给后续”，但 `docs/19-IMPLEMENTATION-BACKLOG.md` 在 TASK-061 后直接进入 TASK-070；全项目没有 TASK-062~069。
- `docs/20-TRACEABILITY-MATRIX.md` 把 PR-006 分阶段生成映射到 TASK-011、040~059，却没有映射一个负责整 App 调度的任务。

这是本轮发现的最重要计划偏差。它会导致开发持续增加底层模块，却没有一个可验收任务负责把用户点击、预算、Job、Stage、Provider、提交、阅读和恢复串成真正闭环。

处理要求：在 TASK-061 收口后立刻补独立任务包，至少拆成：

1. `TASK-062` 总 runner 与 phase 分发，只接 Fake Provider；
2. `TASK-063` 本地恢复/未知结果消费入口；
3. `TASK-064` 数据目的地确认 + 三层预算数据库硬门；
4. `TASK-065` 从确认页到首章可读的全链离线 E2E；
5. `TASK-066` 用户明确授权后的受控真实 Provider 小规模验收。

编号可在正式规划时调整，但不能继续用“后续接线”代替可验收任务。

### P1-03：费用保护还不是所有小说请求都绕不过去的硬门

傻瓜式解释：现在有一个会算“最多花多少钱”的计算器，但它还没有装在付款通道前面。

证据：

- `BudgetEngine` 只有领域逻辑和测试，正式 `src/main` 没有调用方。
- 数据库有 Usage Ledger，但没有 REQUEST/BOOK/DAILY 三层预算计数器与原子 reserve/settle 完整链。
- 当前确认页明确显示价格目录不可用。
- 外部目标 host 的小说内容发送确认仍由 TASK-110 负责。

当前不会造成小说生成扣费，因为总 runner 不存在。将来若先接真实 Provider、后补预算，就会成为费用失控漏洞。

硬要求：真实小说请求开放前，预算预留、最终结算、未知用量、跨日恢复、目标 host 确认必须全部在数据库与发送许可中形成不可旁路的事务证据。

### P1-04：自动备份关闭是正确的，但手动备份没有接入

傻瓜式解释：系统不会偷偷把私人小说传到云端，这是好事；但现在也没有“自己保存一个保险箱副本”的按钮。

证据：

- `AndroidManifest.xml` 设置 `allowBackup=false`。
- Android 旧/新备份规则都排除了全部域。
- `core:backup` 有分块加密和原子文件底座。
- 正式 App 没有 `ChunkedEncryptedBackupCodec`/`AtomicBackupFiles` 调用方，也没有 SAF 创建/打开文档入口。

影响：卸载 App、清除数据、设备损坏、Keystore 丢失时，当前本地内容无法由用户恢复。

处理要求：在用户开始保存真实小说前完成 TASK-100~102，而不是等到发布最后才补。

### P1-05：书已经能保存，但用户没有入口再次打开

傻瓜式解释：仓库里已经放进了一本书，但 App 没有“我的书架”这扇门。

证据：

- `ZhijuanApp` 只有 LOADING、DISCLOSURE、CONNECTION_SETUP、CONNECTION_LIST、CREATE_BOOK、COST_CONFIRMATION 六个目的地。
- 有连接时重启会直接进入 CREATE_BOOK。
- `app/src/main` 没有书架、小说详情、阅读器或目录 UI。
- 创建成功后只保留当前内存中的 `pendingBookId`，没有供用户浏览全部已保存书籍的页面。

数据本身并未因此丢失，但对普通用户而言“保存后取不回来”就是不可用。TASK-090/091/093 应在真实生成前至少交付一个最小书架和滚动阅读器。

### P1-06：TASK-061 还不能真正执行编辑后的跨章重建

当前已经有：用户编辑 CAS、派生失效、重建影响计划、伏笔 rewind、aggregate writer、v14 execution ledger。

当前还没有：

- 从第一个 PENDING step 开始的执行循环；
- 只有真实前驱落库后才创建下一个 memory/tracking Stage 的动态调度；
- 专门重建 permit 的消费边界；
- 跨章失败/恢复/重放全链；
- TEST-033。

因此，任何章节编辑 UI 都不能在这些门禁完成前对用户开放，否则后续章节可能继续使用已经失效的摘要、人物状态或伏笔状态。

### P1-07：本地恢复状态有底层裁决，但没有完整消费入口

`GenerationUnknownResultRecoveryRepository` 能把本地结果恢复场景识别为 `RECOVERY_REQUIRED + LOCAL_RESULT_RECOVERY_REQUIRED`；状态机和维护 Worker 都选择保守处理，不会擅自重发付费请求。

但当前没有总 runner 或 UI 把这个状态交回一个“只读取本地 artifact、绝不重新请求 Provider”的恢复执行器。未来接通生成后，程序若恰好在 VALIDATING/COMMITTING 崩溃，可能安全地卡住，却不能自动继续。

处理要求：把本地恢复入口纳入 TASK-063，并用杀进程测试证明恢复不产生新 Attempt、不增加费用、不重复正文版本。

### P1-08：成人内容规则有代码，真实产出效果仍未被验证

当前代码已经实现的约束包括：

- 成年身份硬门；
- 留白/均衡/细写内外双层映射；
- 关键过程、动作反应、空间、身体状态、感官和相关余波连续性；
- `FADE_SUBSTITUTION`、`BODY_STATE_CONTINUITY_BREAK`、`SENSORY_CONTINUITY_BREAK` 等问题码；
- 固定负例和有限修订门禁。

但这些测试使用本地规则和 Fake Provider，只能证明“系统会提出要求并校验结构”，不能证明任何真实主流模型一定接受、理解并稳定完成中文成人题材。项目文档也正确规定不能通过提示词规避服务商拒绝。

这不是当前代码安全漏洞，但它直接关系到用户最在意的产品效果。需要在费用/目标确认和总 runner 完成后，用用户明确允许的模型做小规模、可停止、可计费的匿名测试集，分别统计：接受率、淡出率、连续性问题率、修订后通过率和单章成本。没有真实 A/B 结果前，不能宣称“成人内容效果已达标”。

## 5. 次要但必须记录的问题

### P2-01：Debug 构建有两个导出的测试组件

`app/src/debug/AndroidManifest.xml` 中：

- `M0DataSyncProbeService` 为 `exported=true`；
- `Task048ForegroundProbeReceiver` 为 `exported=true`，暴露 SEED/QUERY/START 三个固定 action。

它们不进入 Release，但如果把 Debug APK 长期装在真实设备上，同设备其他 App 可以触发测试写入和前台服务。建议加 signature 权限，或改成不导出并由 instrumentation 显式调用。

### P2-02：开始前“确认”仍只是内存 UI 状态

费用确认成功后只修改 `rememberSaveable` 文案，没有把确认版本、时间、host、价格状态写进数据库。当前没有生成，因此没有直接后果；未来必须让确认记录成为 RequestIntent 前的持久硬证据，快照/hash/host/价格变化时自动失效。

### P2-03：仍保留旧提交仓库，未来存在误接旁路风险

`ChapterGenerationCommitRepository` 是 public class，`commit` 也是 public；当前正式代码没有调用方，所以不是现有旁路。但总 runner 开发时容易误用它绕开 TASK-059 的唯一 final executor/coordinator。建议在总 runner 落地时退役、降可见性或增加构建级禁止引用测试。

### P2-04：正式状态文档还有一处明确漂移

- `docs/22-WORK-STATUS.md` 与 `docs/19-IMPLEMENTATION-BACKLOG.md` 正确把 TASK-059 标记为“模块边界完成、总 runner 未完成”。
- `docs/17-ACCEPTANCE-CRITERIA.md:206` 仍写成“TASK-059 完成……后”，并保持未勾选。

这会让后续 AI 重复实现 TASK-059，或错误判断阅读开放条件。应改成“TASK-059 已完成底层最终提交；阅读开放仍等待总 runner、预算、书架/阅读器与 E2E”。

### P2-05：Release 可以构建，但还不是可交付安装包

- 当前 `versionCode=1`、`versionName=0.1.0`。
- Release 启用 R8 与资源压缩，但没有正式签名配置，生成的是 unsigned APK。
- 没有完成覆盖安装、签名升级、许可证页、发布材料和 OEM 实机验收。

### P2-06：没有自动化第三方依赖漏洞扫描

版本目录集中管理了 AndroidX、Room、SQLCipher、OkHttp 等依赖，但仓库中没有 OSV/OWASP Dependency-Check/Dependabot/Renovate 一类可重复的 CVE 门禁。本轮人工检查没有能力证明“所有第三方依赖当前无漏洞”。

OkHttp 官方也明确建议持续保持更新；当前 5.3.0 与官方仓库示例一致，但“版本较新”不等于经过完整 CVE 审计。发布前应新增锁文件/SBOM、已解析依赖清单和自动漏洞扫描，并为无法升级的告警留下书面豁免。

官方参考：<https://github.com/square/okhttp>

### P2-07：敏感内容的屏幕隐私能力尚未实现

正式代码中没有 `FLAG_SECURE`、应用锁、生物识别或最近任务缩略图遮挡。当前还没有阅读器，所以敏感正文尚不可见；在成人内容阅读器开放前，应按 TASK-097 决定默认策略，并给用户一个清楚、低操作量的总开关。

### P3-01：核心文件已经偏大，后续接线容易引入维护错误

生产 Kotlin 中：

- 大于 1,000 行的文件：4 个；
- 大于 500 行的文件：24 个；
- 大于 300 行的文件：66 个。

最大的四个分别约 1,497、1,449、1,383、1,196 行，全部位于数据库上下文组装、DAO 或触发器守卫区域。它们不是已确认 bug，但在总 runner、预算和重建继续接线时，应优先通过小型 facade、专用 permit 和契约测试控制复杂度，而不是继续让调用方直接进入巨型 DAO。

## 6. 已验证通过的关键安全基础

以下通过项只代表当前代码与本轮验证范围，不代表 App 已完成：

- 源码与 5 个 APK 的密钥扫描通过，工作报告目录已纳入扫描。
- Android 系统自动备份与设备迁移的全部数据域都被排除。
- 最终 AI 候选的正文、记忆、追踪、一致性、Usage 与 Stage/Job 提交具有同事务边界。
- 当前正式源码没有发现旧 `ChapterGenerationCommitRepository`、`LibraryDao.commitChapterVersion` 或新 final executor 的实际生产调用方，因此暂未形成发布旁路。
- TASK-060 的旧数据 FTS 回填、完成标记与 token v2 已完成，报告 82 的旧书静默漏召回问题已关闭。

## 9. DeepSeek 复核结论与 Sol 取舍

DeepSeek V4 Flash 以 `read-only`、`max` 运行约 9 分 54 秒，没有修改文件。它正确补充了：

- Debug probe service/receiver 的导出暴露面；
- 费用确认只存在内存，没有持久证据；
- BudgetEngine 仍无生产调用；
- FTS 回填、安全扫描和 Release 构建旧问题已经修复；
- 当前没有总 runner，也没有小说生成 Provider 调用入口。

Sol 没有直接照抄以下结论：

- DeepSeek 用普通 `git status --short` 得到 148 项；该输出会把未跟踪目录折叠。Sol 使用 `-uall` 重算后，精确文件级数量是 185，其中 134 个未跟踪文件。
- DeepSeek 判断正式文档完全一致；Sol 核对出 `docs/17-ACCEPTANCE-CRITERIA.md:206` 仍保留 TASK-059 的旧状态。
- DeepSeek 没有指出总 runner 缺少任务编号；Sol 对 backlog 和 traceability 全量搜索确认 TASK-062~069 完全不存在，这是当前最重要的计划漏洞。
- DeepSeek 把未持久化确认列为当前 S2；Sol 将它归为未来真实生成前的门禁，因为当前确认不会启动 Job 或请求，尚无直接损害。

## 11. 最终判断

织卷当前的底层代码质量和测试投入明显高于普通原型，未发现需要推倒重来的架构性灾难；TASK-061 Phase 2B3B1 的事务边界也可靠。

真正的偏差是开发重心长期集中在数据库和生成零件，用户价值闭环落后：**没有被编号的总 runner、没有书架/阅读器、没有手动备份、没有模板复制、没有真实预算门禁。** 如果继续只追加底层仓储，代码量会继续增长，App 仍然不能用。

下一阶段应先保存 Git 现场并完成 TASK-061，然后立即补正式的总 runner 任务链；此后以“首章能安全生成并立即阅读”为验收目标推进，而不是再以“新增一个底层类并通过测试”作为产品完成度替代品。
