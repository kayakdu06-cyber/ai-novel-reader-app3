# 织卷工作汇报 08：M0 二次复评与严重遗漏修正

> 日期：2026-08-01  
> 结论：可以继续开发，但 M0 不能宣告完成；新增两项 P0 技术尖峰

## 1. 复评范围

本次把产品需求、功能清单、技术架构、数据模型、状态机、安全与备份、测试计划、验收标准、开发清单、需求追踪矩阵、ADR 和已经完成的 M0 代码证据重新交叉核对，重点寻找会造成以下后果的遗漏：

- 丢失或覆盖小说；
- 泄露 API 密钥或正文；
- 崩溃后重复付费；
- 到后期才发现架构不可行；
- 产品承诺与实际模型能力不一致。

## 2. 新发现的两项严重遗漏

### 2.1 加密备份与原子恢复缺少早期可执行证明

现有文档已经规定“先导入临时区、完整校验、成功后再替换”，测试计划也包含错口令和损坏包，但原 M0 没有对应尖峰。若等到 E9 才发现大备份包内存爆炸、恢复中断覆盖当前库或 Windows/Android 文件替换语义不成立，会直接造成丢书和大规模返工。

处理：新增 `TASK-008A`，在 M0 先证明流式格式、认证、损坏检测和不覆盖当前数据的提交边界。正式产品能力仍由 `TASK-100/101` 完成。

### 2.2 自定义中转站的秘密边界缺少代码级验证

织卷允许用户填写任意主流兼容中转站。只做“连接成功”不足以防止 HTTP 明文、跨 host 重定向携带 Authorization、证书错误被错误忽略或 URL 规范化改变目的地。这会同时造成密钥泄露和错误付费。

处理：新增 `TASK-008B`，在 M0 先用本地假服务验证 HTTPS 策略、重定向剥离、证书错误分类和日志脱敏。正式网络层仍由 `TASK-021` 完成。

## 4. 产品承诺校正

“接入主流模型”是可实现的协议能力；“每个主流模型都能生成用户要求的全部内容尺度”不是 App 可以保证的能力。不同提供方和中转站会有不同策略，且可能变化。织卷应当：

- 对实际成功、能力不足、策略拒绝分别记录；
- 给出可理解的模型/连接状态；
- 不把策略拒绝当网络错误无限重试；
- 不通过改写请求或切换未授权端点规避提供方策略；
- 允许用户自行选择符合其用途和当地规则的服务。

这项约束已落在能力登记表、标准错误和连接诊断任务中。

## 5. 密钥处理复核

- 用户提供的现有 DeepSeek 密钥没有写入项目文件、文档、报告、构建配置或命令日志。
- 后续真实联调只通过 App 内的安全输入与 Keystore 路径进行，不把密钥拼进开发命令或测试夹具。
- 因密钥曾以消息形式提供，建议把它视为短期测试凭据；进入长期自用或产生较高费用前在服务商控制台轮换。

## 6. 文档修正

- M0 交付清单新增加密备份/原子恢复尖峰和自定义端点网络安全尖峰。
- M0 退出闸门从模糊的“六项尖峰”改为“所有 E0 P0 风险项有可复现实验”。
- Backlog 新增 `TASK-008A` 与 `TASK-008B`，并成为 ADR 收束前置依赖。
- 追踪矩阵补入两项遗漏、服务商内容能力边界和用户测试密钥的落盘禁令。
- 工作状态明确：M0 尚未关闭，ADR-003/004 仍为 Proposed。

## 7. 复评后的开发顺序

1. `TASK-008A`：加密备份与原子恢复最小尖峰。
2. `TASK-008B`：自定义端点网络安全最小尖峰。
3. 收束 ADR-001~005 和 M0 结论。
4. 进入 M1 正式 schema、Keystore secret store、迁移框架和安全网络层。

## 8. 最终判断

没有发现需要推翻“原生 Android、本地优先、分阶段生成、持久状态机、统一适配层、模板不可变版本”这些核心架构的缺陷。真正严重的缺口是两项安全/可靠性尖峰缺失，现已进入硬闸门。完成它们之前不把 M0 标成完成；完成之后才允许进入 ADR 收束。
