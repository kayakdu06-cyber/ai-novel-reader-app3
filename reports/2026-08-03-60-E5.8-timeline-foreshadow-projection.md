## 2. 二次评审关闭的严重风险

### 2.1 不能只保存伏笔“当前状态”

旧 `foreshadow_item` 只能告诉系统现在是 PLANTED、DEVELOPING 或 RESOLVED，无法证明它在哪一章发生过什么变化。更严重的是：一条线索可能在第 2 章埋设、第 8 章发展、第 20 章回收；编辑第 8 章后，当前记录的来源已经指向第 20 章，若只检查当前来源，会错误保留一条已经失去中间因果的回收结果。

本轮新增 `foreshadow_transition` 追加式台账。任何旧章节版本被替换时，失效逻辑检查整条转换历史；只要当前伏笔曾依赖该旧版本，当前投影整体变为 STALE。

### 2.2 不能把所有悬念都登记成伏笔

PLANT 只接受本章已出现的具体新线索，描述不得与既有或本章新线索重复。模型不能把普通信息、尚未发生的计划或每个未解问题都写进伏笔表。

### 2.3 不能让模型随意“放弃”难写的伏笔

ABANDON 只允许从 PLANNED/PLANTED/DEVELOPING 进入 ABANDONED，并且正文必须明确使原安排不可能、尚未完成回收，`confidenceMicros` 必须为 1,000,000。不确定时不输出操作，保留原状态。

### 2.4 不能从旧快照继续付费或落库

请求同时绑定：

- 最终章节版本 ID、正文 SHA-256、章节 ID 和序号；
- 同版本 `chapter-memory.v1` 快照 hash；
- 提取前有效伏笔快照 hash；
- 当前故事实体快照 hash。

RequestIntent 写入后、Provider 打开前，以及最终提交事务内都会重新计算。任一变化都会失败关闭；联网前变化的测试确认 Provider 调用数为 0。

## 3. 已实现契约

### 3.1 时间线

- 每章最多 64 个事件；
- 只记录正文真实发生、会影响顺序或后续约束的事件；
- 参与者必须是故事圣经中的已知实体；
- 地点非空时必须是已知 LOCATION；
- 事件带故事时间表达、顺序约束和短证据；
- 本章顺序键稳定，重放不会产生另一套顺序或 ID；
- 高强度场景不能抹掉实际发生的先后、地点、参与者及相关身体/关系余波，但测试和报告不保存示例正文。

### 3.2 伏笔状态机

| 操作 | 允许旧状态 | 新状态 |
|---|---|---|
| PLANT | 无 | PLANTED |
| DEVELOP | PLANTED / DEVELOPING | DEVELOPING |
| RESOLVE | PLANTED / DEVELOPING | RESOLVED |
| ABANDON | PLANNED / PLANTED / DEVELOPING | ABANDONED |

既有伏笔必须精确回显原 ID、描述、重要度和旧状态；可见实体只能增加，不能删除；同一条伏笔在同一章最多变化一次。`RESOLVED` 与 `ABANDONED` 不允许被模型重新打开。

## 4. schema v8 与原子事务

新增：

- `chapter_tracking_projection`：保存整章投影的来源、输出/payload hash、模型快照、计数和状态；
- `foreshadow_transition`：保存每次状态操作、旧/新状态、来源章节版本、Generation Stage、顺序和证据；
- `foreshadow_item` 的同书复合唯一父键，保证转换不能跨书引用伏笔。

数据库触发器拒绝跨书、错误章节/Stage、计数越界和非法操作。应用提交事务进一步验证受保护 artifact 修订、原始/规范 hash、模型快照、租约、来源快照、伏笔旧状态 CAS 和完整 payload hash。

一次成功提交同时完成：时间线、新伏笔、既有伏笔状态 CAS、转换台账、投影头、FINAL Usage、Stage 输出、下一 Stage 或 Job 终态。任一步失败整笔回滚。完全相同的成功重放只回读原数据，不重复插入。
