> 审计日期：2026-08-05

> 审计方式：DeepSeek V4 Flash `max` 独立只读审计 + Sol 源码交叉复核 + 本地离线构建验证  
> 本次性质：只审计、只出报告；没有修改业务代码，没有调用 App 内真实生成 API，没有操作实体设备

## 1. 给非技术使用者的结论

织卷目前**不是一套已经可以放心长期使用或发布的完整 App**，但也不是“底层已经烂掉”。现状更准确地说是：

- 数据加密、Android 备份隔离、明文网络禁用、AI 生成结果的原子提交等底层安全基础做得较扎实。
- 当前代码可以完成全模块 JVM 测试、Debug 构建和 Release/R8 组装。
- App 仍没有把整套小说生成流水线串起来，创建页确认后不会真正开始生成小说。
- 费用控制目前只有规则计算器，尚未成为每次真实生成请求都绕不过去的数据库硬门禁。
- TASK-060 新搜索索引只覆盖新写入的数据，旧书升级后的首次回填还没实现，会造成“旧内容明明存在，但搜索不到”。
- 当前安全扫描器既会误报普通文件名，又会漏扫整个工作汇报目录，不能作为可信的上传前密钥门禁。
- 当前大量开发成果没有进入 Git 提交，并且副本没有远程仓库；电脑或目录出问题时，无法仅靠 Git 恢复现在的成果。

综合判定：

| 使用场景 | 结论 | 原因 |
|---|---|---|
| 继续本地开发 | **可以** | 编译和 JVM 测试正常，底层结构可继续演进 |
| 体验当前创建/连接界面 | **可以，但谨慎使用完整连接测试** | 完整连接测试会在明确确认后发出最多 16 tokens 的真实小请求 |
| 用它自动生成整本小说 | **不可以** | 总 runner 尚未接入，界面也明确显示没有调用模型 |
| 把已有旧书交给新搜索功能 | **不可以依赖结果完整性** | 旧数据回填尚未实现 |
| 作为日常唯一写作工具 | **暂不建议** | 阅读器、模板复制、备份恢复、完整生成闭环等尚未完成 |
| 发布、分发或上传安装包 | **不可以** | Release 未签名，统一门禁不可靠，关键产品和费用门禁未完成 |

## 2. 风险等级说明

- **P0 / 紧急**：已经存在可直接造成密钥泄露、付费失控、正文永久损坏或远程利用的问题。
- **P1 / 发布阻塞**：当前未必能被用户触发，但在继续接通真实生成、升级旧数据或发布前必须解决。
- **P2 / 重要**：不立即造成灾难，但会造成卡死、错误判断、难以恢复或长期维护风险。
- **P3 / 一般**：文档、体验或工程卫生问题，不阻塞当前开发。

本次没有确认到当前可达路径上的 P0 漏洞，也没有发现实际密钥已经留在源码、报告或 APK 中。下面列出的主要问题是 P1/P2。

## 3. 已确认的问题

### P1-01：统一密钥扫描器同时存在误报和漏报

**傻瓜式解释：** 现在的“安检门”会把普通工作汇报文件名当成钥匙报警，但真正放在 `reports` 文件夹里的钥匙，它又完全不检查。

证据：

- `scripts/security-scan.ps1:18` 使用 `sk-[A-Za-z0-9_-]{20,}`，会把 `task-059-compatibility...`、`task-060-production...` 里的 `sk-...` 子串误识别为密钥。
- `scripts/security-scan.ps1:35` 明确排除了 `reports/**`。
- 本次统一门禁实际因 3 个任务包里的普通报告文件名而失败，并非发现真实密钥。
- 另行使用带左边界的更精确规则，覆盖源码、文档、`reports` 和 3 个现有 APK 后，源码命中文件数为 0，APK 命中条目数为 0。

影响：

- 开发者可能因为频繁误报而忽略真正报警。
- 如果以后误把真实 API Key 写进工作汇报，统一门禁仍可能显示通过。
- 目前不能把 `SECURITY_SCAN_OK` 当成完整的“可以上传”证明。

修复要求：

1. 给 `sk-` 规则增加可靠的左边界，避免匹配 `task-...`。
2. 取消对整个 `reports` 目录的排除，只排除明确的机器生成二进制或受控临时目录。
3. 给扫描器补三类自动测试：真实密钥样式必须拦截、`task-060` 必须放行、报告目录中的 canary 必须拦截。

### P1-02：当前工作成果没有形成可恢复的 Git 基线

**傻瓜式解释：** 文件现在都还在，但很多成果只存在这一个本地目录里。Git 的“存档点”没有包含它们，远端也没有备份。

本次检查结果：

- 当前 HEAD：`8ce774429da1c3f7139a221bc241c34d81a2efdd`。
- `git status --porcelain` 共 87 项：37 项已跟踪修改，50 项未跟踪入口。
- 当前没有任何 Git remote。
- `git diff --check` 通过，但这只说明补丁格式正常，不等于成果已经备份。

影响：

- 仅从 HEAD 无法重建 TASK-059 完成状态和 TASK-060 Phase 1A/1B 当前现场。
- 本地磁盘、目录或误操作出问题时，报告和代码可能一起丢失。
- 后续审计无法把测试证据准确绑定到一个不可变提交。

修复要求：先把当前现场按可审查阶段整理成本地提交，再连接用户指定的私有远程仓库并推送。提交前必须先修复密钥扫描盲区并重新扫描。

### P1-03：旧书搜索索引没有首次回填

**傻瓜式解释：** 新写的内容会放进新目录卡片，但升级前已经存在的旧内容没有人补卡片。因此内容没有丢，搜索却会假装它不存在。

证据：

- `ZhijuanMigrations.kt:502` 的 `MIGRATION_8_9` 创建新搜索表、FTS 表和同步触发器。
- `ZhijuanMigrations.kt:529-535` 只创建 FTS 与增量同步触发器，没有从六类旧权威数据源生成历史索引的回填语句或完成标记。
- `docs/ai/CURRENT-CONTEXT.md:135` 明确记录 TASK-060 仍未完成，下一步包含旧数据首次回填。
- Phase 1C 任务包已经定义 v10 的按书完成标记和可恢复回填方案，但尚未落地。

影响：数据库从 v8 升到 v9 后，旧书的召回结果会静默缺失。当前搜索 UI/完整召回尚未接入，因此现在还不是用户可触发故障，但一旦接入就会成为真实数据正确性问题。

修复要求：完成 TASK-060 Phase 1C，在第一次使用某本书的召回前，以单个可恢复事务重建六类来源，并写入加密的按书完成标记；必须补 v8→目标版本的迁移测试和中断重试测试。

### P1-04：真实小说生成没有总调度器，费用硬门禁也未接入请求路径

**傻瓜式解释：** 发动机零件已经做了很多，但还没有总控制器把它们按顺序接起来；“最多花多少钱”的计算器也还没有变成每次发请求前必须刷过的一道闸门。

证据：

- `ChapterFinalCandidateCommitStageExecutor.kt:52` 自己标注为“future total runner”的入口。
- 在 `src/main` 中没有找到该 final executor 的生产调用方。
- `ZhijuanApp.kt:216` 明确向用户显示“生成执行器尚未接入，当前没有调用模型”。
- `BudgetEngine` 目前是纯规则引擎；没有找到小说生成生产路径对三层预算进行数据库原子预留、结算和释放的接线。

当前真实付费例外：

- 连接向导的“完整检查”会在用户确认后调用真实 Provider。
- `ConnectionWizardScreen.kt:374` 和 `:430` 已明确告知固定测试语句、最多 16 tokens、可能产生极少费用，且不发送小说或人物资料。
- `ConnectionWizardGateway.kt:327-328` 确实启用了最小生成验证并记录费用确认。

因此，正确结论不是“App 完全不会联网付费”，而是：**小说生成目前不可达；只有用户明确确认后的、严格限制为最多 16 tokens 的连接测试可能产生极少费用。**

修复要求：总 runner 接入真实 Provider 之前，先完成数据库级三层预算预留/结算、目标地址二次确认、未知结果结算、暂停/停止安全点和全链路恢复，任何路径不得旁路。

### P1-05：Release 能组装，但当前只是未签名包，统一门禁也没有真正组装 Release

证据：

- `app/build.gradle.kts:19-20` 仍为 `versionCode = 1`、`versionName = "0.1.0"`。
- Release 启用了 R8/资源压缩，但没有正式 `signingConfig`。
- `scripts/verify-build.ps1:29-31` 只执行 `test`、`:app:assembleDebug` 和 `:app:processReleaseManifest`，没有执行 `:app:assembleRelease`。
- 本次单独执行 `:app:assembleRelease` 成功，产物为 `app-release-unsigned.apk`，大小 11,265,392 bytes。

影响：统一门禁即使通过，也不能证明 Release/R8 真正可构建，更不能证明 APK 已签名或适合安装分发。

修复要求：发布前单独设计本机私密签名流程；统一门禁加入 `assembleRelease`、签名状态检查、Release APK 密钥扫描、安装/升级验证和版本号检查。签名密钥不得进入仓库。

### P2-01：本地提交崩溃恢复会进入一个尚无消费入口的状态

**傻瓜式解释：** 如果程序恰好在“内容已经生成完、正在写进正式书库”的阶段崩溃，维护程序会把任务放进“需要本地恢复”的盒子；但现在还没有完整按钮或总调度器把它从这个盒子拿出来继续完成。

证据链：

1. `GenerationMaintenancePolicy` 会审计过期的 `VALIDATING` 和 `COMMITTING` Stage。
2. 成功的请求在这两个本地阶段会被判定为 `RECOVER_LOCAL_RESULT_WITHOUT_NEW_REQUEST`。
3. `GenerationUnknownResultRecoveryRepository.kt:435-479` 把 Stage 变为 `RECOVERY_REQUIRED`，Job 变为 `NEEDS_ACTION`，原因是 `LOCAL_RESULT_RECOVERY_REQUIRED`。
4. `ChapterFinalCandidateCommitStageExecutorV1` 只接受 `READY`、`PREPARING`、`COMMITTING`、`SUCCEEDED`；没有接受 `RECOVERY_REQUIRED`。
5. 全部生产源码中没有找到把这个本地恢复状态重新交给 final executor 的入口。

影响：当前总 runner 未接入，所以这还是潜伏问题；一旦接通自动生成，崩溃后可能永久卡在“需要操作”，而不是安全、幂等地继续本地提交。

修复要求：在接通总 runner 前增加明确的本地恢复执行器/确认入口，以持久证据重新获取合法 lease，只做本地 artifact 恢复和原子提交，绝不能再次调用 Provider。

### P2-02：正式状态文档已经发生矛盾

证据：

- `docs/17-ACCEPTANCE-CRITERIA.md:149`、`:206`、`:230` 仍把 TASK-059 的主要内容写成待完成。

影响：后续 AI 或开发者可能从错误起点继续，重复实现已经完成的模块，或把未完成的 TASK-060 误判成已完成。

修复要求：在下一阶段开发前统一三份正式状态来源，并明确“TASK-059 模块完成”不等于“整 App 已能生成小说”。

## 4. 没有发现问题的关键基础

以下结论仅限本次静态检查和离线验证范围：

- 主数据库通过 SQLCipher 打开，`ZhijuanDatabase.kt:114-122` 使用加密 open-helper 和显式迁移，没有发现 `fallbackToDestructiveMigration`。
- 数据库口令失败或关闭时会清零内存字节数组，见 `ZhijuanDatabase.kt:125-145`。
- Android Keystore 使用 AES-GCM 管理本地密钥。
- `AndroidManifest.xml:11-21` 禁止系统备份并禁止明文网络。
- 备份排除校验覆盖 source、debug、release 三种清单并通过。
- 最终候选正文、派生记忆、追踪和一致性结果在同一个 SQLCipher 事务中发布；没有找到旧提交仓库或 `LibraryDao.commitChapterVersion` 的生产调用方。
- FTS 文档生成器对可检索 token 采用 ASCII 约束、长度/数量限制和确定性构造；新数据的六类增量索引写入与权威数据处于同一事务。
- 没有发现生产源码中的明文日志输出小说正文、提示词或 API Key。
- 精确密钥规则复扫源码、文档、报告和 3 个 APK 后，没有发现真实凭据样式。

这些“通过项”不代表整 App 已经完成，也不替代后续实体设备、升级、断电恢复和真实 Provider 的受控验收。

## 7. 建议的修复顺序

按“先防丢、再封门、最后接真实生成”的顺序执行：

1. **保存当前开发现场**：修复扫描器后，对当前 WIP 做完整精确复扫，整理并提交 Git，再推送到用户指定的私有远程。
2. **修复安全扫描器**：消除 `task-060` 误报，纳入 `reports`，补 canary 回归测试。
3. **完成 TASK-060 Phase 1C**：旧书按书回填、完成标记、幂等重试和迁移测试。
4. **补本地提交恢复闭环**：让 `RECOVERY_REQUIRED + LOCAL_RESULT_RECOVERY_REQUIRED` 能只靠本地证据继续，不重复付费请求。
5. **实现三层预算数据库硬门禁和目标地址确认**：完成之前不得把小说生成总 runner 接到真实 Provider。
6. **接总 runner**：只允许调用已经审计的各 Stage 专用入口，尤其是唯一 COMMIT_CHAPTER executor，禁止恢复旧旁路。
7. **补产品闭环**：模板复制、阅读器、边生成边阅读、备份恢复、失败处理。
8. **发布收口**：统一状态文档、正式签名、版本号、`assembleRelease` 门禁、APK 扫描、API 35/API 30、升级/杀进程/长时间运行验收。

## 8. 最终判断

当前系统适合继续开发，但不适合把“已经能构建”解释为“已经能安全生成整本小说”。最严重的现实风险不是某个远程黑客漏洞，而是：**本地成果尚未形成可恢复版本、密钥门禁不可信、旧书索引会静默缺失，以及未来本地提交崩溃后可能卡死。**

在完成第 7 节前 5 项之前，不应开启真实小说生成；在全部 8 项完成并重新验收前，不应发布或作为唯一创作工具。
