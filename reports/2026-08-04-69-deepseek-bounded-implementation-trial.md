# 工作汇报 69：DeepSeek 小任务真实编码试运行

> 日期：2026-08-04  
> 所属任务：TASK-059 第六阶段  
> 结论：试运行有效；代码可用，但后续必须进一步压缩读取范围

## 1. 本次试验目标

本次没有让 DeepSeek 承担整段业务开发，只拆出一个可以单独验收的小缺口：当一致性检查决定自动修订时，修订请求种子的 `generationId` 必须与当前冻结的一致性检查请求属于同一个生成任务。若两者不一致，必须在创建修订请求前立即拒绝。

任务只允许修改一个实现文件和一个测试文件，不允许触碰数据库、Provider、状态机、文档或其他模块；使用最高推理强度，按用户要求不设置总 Token 上限，但保留 15 分钟运行时限和项目隔离。

## 2. DeepSeek 实际交付

- 在 `ChapterCandidateConsistencyRoutingPlannerV1` 的自动修订分支增加同一生成任务校验；
- 校验发生在读取冻结的修订种子之后、构造修订请求之前；
- 新增“来自其他生成任务的修订种子必须被拒绝”负例测试；
- 保持接受路径、额度耗尽路径和正确任务 ID 的自动修订路径不变；
- 实际只触碰任务包允许的两个文件，没有写入其他项目文件；
- 没有调用织卷 App 的真实 Provider API，也没有写入物理设备。

## 3. Sol 独立复核

Sol 没有直接相信 DeepSeek 的自述，而是重新检查了文件时间、Git 范围、代码位置、测试报告和文件差异。

复核结果：

- 修改范围正确，未发现越界写入；
- 实现位置正确，错误任务 ID 会在请求构造前被拒绝；
- 中文源码未被破坏；
- DeepSeek 自测报告为 8 项测试全部通过；
- Sol 使用离线模式强制重新执行同一测试类，结果仍为 8 项通过、0 失败、0 错误、0 跳过；
- `git diff --check` 通过。

## 4. 发现的问题

代码结果合格，但执行过程不够节省：

- 一个很小的任务累计读取输入 648,893 Token，其中 612,096 Token 命中缓存；输出 10,212 Token，推理输出 4,893 Token；
- DeepSeek 为定位一个直接引用的类型，对 `feature/generation` 主源码做了递归查找，超过任务包建议的最小读取范围；
- 最终工作说明发生控制台中文乱码，但源码和测试文件没有乱码；
- 测试文件原本就存在 LF/CRLF 混合换行，本次没有扩大或统一该问题。

这说明 DeepSeek 已经能够产生可审查、可运行的真实代码差异，但当前任务提示仍给了它过多自行探索空间。后续任务包必须直接给出相关类型所在文件、目标函数和验收命令，并明确禁止递归扫描，避免用大量上下文换取一个很小的修改。

## 5. 工作流结论

本次试运行判定为有效，可以继续使用以下协作方式：

1. Sol 先审计并把缺口拆成一个小闭环；
2. DeepSeek 只修改明确列出的少量文件；
3. DeepSeek 必须交付真实代码差异和定向测试；
4. Sol 逐行审查差异并独立重跑测试；
5. 未产生差异、越界修改或测试失败均视为该任务未交付，由 Sol 收回处理；
6. 不设置总 Token 上限，但继续保留单任务时间限制、最高推理强度、目录隔离和真实 API 禁用规则。
