## 1. 本阶段目标

把“准备调用模型”与“已经允许打开网络连接”拆成两个可验证的步骤。任何生成请求必须先在本地加密数据库中留下完整、可恢复的请求意图，数据库事务成功后才可能取得一次性发送许可；只要审计记录、用量占位、阶段状态或租约中的任意一项不成立，就不能进入 Provider 传输层。

这项工作解决三类高风险问题：

- App 崩溃后无法判断请求是否可能已经发生；
- Attempt 已写入但 Usage 或 Stage 没有同步更新，造成恢复时重复发送；
- 旧执行器持有过期的内存对象，仍然在租约失效后打开网络连接。

## 2. 已完成的实现

### 2.1 原子落库后才签发许可

新增 `GenerationRequestAuditRepository`，由它统一执行发送前审计：

1. 验证 RequestIntent 草案；
2. 在同一个 Room 事务中创建 `INTENT_RECORDED` Attempt；
3. 同时创建 `UNKNOWN / PROVISIONAL` Usage 占位；
4. 同时把 Stage 推进到 `REQUEST_INTENT_RECORDED` 并增加 attempt 计数；
5. 事务提交后重新读取三类证据；
6. 只有证据完全一致才构造一次性 `PersistedRequestSendPermit`。

其中任意写入冲突或事务失败时，Attempt、Usage、Stage 和计数全部回滚，不会留下半条审计记录，也不会返回发送许可。

### 2.2 打开 Provider 前再次核对租约

初版设计中，一次性 permit 可以直接在内存中 claim。二次自审发现：permit 可能已经签发，但执行器在真正打开网络连接前停顿超过租约时限；如果仍允许只凭内存对象继续发送，TASK-041 的旧执行器栅栏就会被绕过。

最终改为只能通过 `GenerationRequestAuditRepository.claimForProviderOpen(...)` 取得发送授权。该入口会再次：

- 核对 Attempt、Usage、inputHash、attemptNo 和 intent 时间；
- 使用同一份 owner + acquiredAt 租约凭证刷新 Stage 心跳；
- 在租约已过期、已被接管或证据被修改时失败关闭；
- 以一次性方式烧毁原 permit，失败后也不能重复 claim。

因此，“事务曾经成功”不等于“未来任意时刻都能发送”。真正的网络边界仍要求当前数据库事实和当前租约同时有效。

### 2.3 请求已发送的可审计推进

`markRequestSent(...)` 只接受内部构造的 `ClaimedRequestSend`，并再次核对持久化证据后，以原子事务完成：

- Attempt 从 `INTENT_RECORDED` 推进到 `SENT`；
- 写入 Provider 请求 ID 和发送时间；
- Stage 从 `REQUEST_INTENT_RECORDED` 推进到 `STREAMING`。

当前阶段没有真正打开 Provider，也没有发出网络请求；这里完成的是网络执行器后续必须服从的审计契约。

### 2.4 审计快照的敏感信息门禁

请求与 Provider 快照必须是有界、严格的 JSON Object：

- ID 仅允许安全字符且最长 128；
- inputHash 必须是 64 位小写 SHA-256；
- 快照非空且单份不超过 65,536 个字符；
- 流式草稿引用最长 1,024；
- 时间戳不得为负，dailyPeriodKey 不得为空且最长 128；
- 拒绝数组、非 JSON、单引号伪 JSON 和超限输入；
- 递归检查对象与数组内的字段名，拒绝 API Key、Authorization、Cookie、密码、token、client secret、credential 等敏感字段；
- 允许只保存本地引用标识，例如 `secretRefId`，不保存密钥值。

公开审计投影不返回请求/Provider 原始快照，DTO、permit 和 claimed authorization 的 `toString()` 也不会输出快照、ID 或 inputHash。
