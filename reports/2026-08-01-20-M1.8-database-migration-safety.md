# 织卷工作汇报 20：M1.8 数据库迁移与防清库

> 日期：2026-08-01  
> 对应：TASK-017  
> 结论：当前全部历史 schema 可安全升级到 v4；真实加密库路径通过；缺失迁移时失败关闭并保留原书

## 1. 本轮关闭的严重风险

此前已有 v1→v2、v2→v3、v3→v4 三段迁移，但测试只分别验证相邻版本和少量书籍字段，仍存在四个严重缺口：

1. 没有验证 v1→v4、v2→v4 这种用户真实跨版本升级；
2. 生产启动与测试分别手工列迁移，未来可能出现“测试有、生产漏注册”；
3. 没有用真实 SQLCipher、Keystore 包装口令和正式数据库工厂迁移旧库；
4. 没有证明缺少迁移时 App 会保留旧书，而不是破坏性清库。

本轮已逐项补齐。

## 2. 唯一迁移注册表

生产数据库版本统一使用 `ZHIJUAN_DATABASE_SCHEMA_VERSION`。所有迁移集中在 `ZhijuanMigrations.ALL`，正式 `EncryptedZhijuanDatabaseFactory` 与测试从同一注册表取路径。

`pathFrom(startVersion)` 会逐段构造到最新版的连续路径；中间任何一段缺失、倒退或跨过目标版本都会立即失败。这样新增 v5 时只需在一个地方登记迁移，测试会同时检查所有历史起点。

## 3. 数据保留范围

从 v1、v2、v3 分别升级到 v4，均核对：

- 书籍创建快照、快照哈希；
- 书籍标题与记录数量；
- 章节、当前正文版本指针；
- 正文内容与正文哈希；
- 数据库完整性和全部外键。

对起始版本中已经存在的能力继续核对：

- v2/v3：生成任务、阶段、请求尝试、用量账本、输出哈希、token 数；
- v3：故事圣经、大纲、大纲节点、记忆头、章节摘要及关键来源指针。

迁移后还验证 v4 模板表和不可变保护触发器已经存在。

## 4. 真实加密生产路径

测试从导出的 v1 Room schema 创建真实 SQLCipher 加密旧库，再交给正式 `EncryptedZhijuanDatabaseFactory` 执行 v1→v4。

结果：

- v4 schema 校验通过；
- 原小说、当前版本指针和哈希保持；
- `PRAGMA integrity_check` 返回 `ok`；
- `PRAGMA foreign_key_check` 为 0；
- 主库及可能存在的 WAL/SHM 文件中，正文 canary 为 0；
- 数据库头不是明文 SQLite 标识。

这条测试覆盖的是真正会交付给用户的 SQLCipher + Room + Keystore 口令路径，不是只测明文 SQLite。

## 5. 禁止破坏性清库

测试人工创建一个 schema version 5 的加密库，里面保存一部夹具小说，再用当前只支持到 v4 的正式工厂打开。

预期和实际结果一致：

- App 拒绝打开不支持的未来数据库；
- 不执行降级或重建；
- 使用原版本重新打开后，schema version 仍为 5；
- 原书、章节、正文、哈希和外键全部保持；
- 加密文件仍搜索不到正文 canary。

这为“没有迁移就停下，绝不偷偷清库”提供了可重复证据。
