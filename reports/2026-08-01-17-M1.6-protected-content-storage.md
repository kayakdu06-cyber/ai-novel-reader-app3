# 织卷工作汇报 17：M1.6 正文、草稿与恢复点加密存储

> 日期：2026-08-01  
> 对应：TASK-015  
> 结论：正式小说正文、流式草稿和迁移恢复点均已进入明确的加密边界，文件/库测试明文扫描为 0

## 1. 本阶段解决的问题

本任务不是简单地“把所有东西各加密一遍”，而是先确定唯一事实源：

- 已完成的正式章节继续以不可变 `ChapterVersion` 存在 SQLCipher Room 数据库中；
- 未完成的网络流只写临时草稿，不直接覆盖正式章节；
- 迁移恢复点使用独立受保护文件；
- 不为正式正文再造一份文件副本，避免数据库版本和文件版本不一致。

因此，“小说、草稿、恢复点”都有保护，但正文仍只有一套真实版本链。

## 2. 正式小说正文保护

正式正文沿用已经验收的生产数据库路径：

- `EncryptedZhijuanDatabaseFactory` 从 `DatabasePassphraseStore` 取得随机数据库口令；
- 口令由 Android Keystore 包装，不写入 Room 或普通设置；
- Room 主库、WAL、SHM 和数据库内索引都由 SQLCipher 统一保护；
- `ChapterVersion.content` 仍保持不可变版本和事务提交约束。

本阶段增强了设备验收：向真实生产库写入唯一小说正文 canary，在数据库保持打开时扫描主库和全部同名 WAL/SHM，关闭后再次扫描，均未找到明文；随后用同一 Keystore 包装口令重开数据库，正文能够正确读取。

## 3. 受保护 artifact 存储

新增 `AndroidProtectedArtifactStore`，用于：

- `STREAM_DRAFT`：未完成的流式章节草稿；
- `DATABASE_RECOVERY_POINT`：迁移或恢复前的数据库恢复点。

文件放在 Android `noBackupFilesDir/content/protected-artifacts`，文件名只含随机 UUID 引用，例如 `artifact-<randomRef>.zjaf`。书名、章节名、jobId 和 attemptId 不进入路径；它们只在加密数据库中通过引用关联。

每个 artifact 有独立 Android Keystore AES-256-GCM key，与 API secret key、数据库口令包装 key 均分离。

## 4. 文件格式与完整性

受保护文件由三个认证层组成：

1. 认证文件头：绑定随机引用、用途、修订号、keyVersion、创建/更新时间和块大小；
2. 认证内容块：默认每块 64 KiB，使用随机 IV，AAD 绑定头摘要、连续块序号和本块明文长度；
3. 认证尾记录：绑定总块数、总明文字节数和 SHA-256。

因此以下修改都会失败：

- 修改 artifact 类型、引用或修订号；
- 密文任意位翻转；
- 删除、重复、插入或调换内容块；
- 截断文件或删除认证尾；
- 在合法尾部追加数据；
- 用错误或已经删除的 Keystore key 读取。

这里使用的是 Android Keystore 提供的标准 AES-GCM，不是自行设计的加密算法。自定义部分只是版本化容器和 AAD 绑定规则。

## 5. 原子草稿检查点

草稿每次换版都必须提供 `expectedRevision`：

- 当前修订为 N 时，只允许 N 的持有者提交 N+1；
- 旧网络回调或重复执行器持有 N-1 时会被拒绝；
- 新版本先写入 AtomicFile 临时状态并同步磁盘，成功后才替换旧版本；
- 输入流中断、磁盘异常或认证写入失败时，AtomicFile 恢复上一份完整密文。

设备测试先成功提交第二版，再模拟过期写入和输入中途抛错，最终读取仍是完整第二版，没有半份文件或旧执行器覆盖。

## 6. 明文生命周期与 App 锁

- `createAndClear`、`replaceAndClear` 消费调用方传入的 ByteArray，并在成功、校验失败或写入失败后清零；
- 小型草稿只通过 `ProtectedArtifactLease` 暂借，不返回长期字符串属性；
- lease 关闭、artifact 被替换/删除或 Store 锁定时，底层明文缓冲立即清零；
- 锁定期间读取内容、验证文件和列出 descriptor 都会被拒绝；
- descriptor 只包含随机引用、类型、修订号、keyVersion 和时间，不包含正文或业务名称。

调用方仍可能在 `withBytes` 回调里主动复制明文，这属于受信任进程内代码边界；Store 能防止普通业务层无意长期持有同一缓冲，但不承诺抵抗已经控制 App 进程的攻击者。

## 7. 大恢复点与内存边界

- 流式写入和读取使用固定 64 KiB 缓冲；
- 文件格式最大明文长度为 16 GiB，防止无限输入；
- 小草稿一次读入内存的公开上限为 4 MiB；
- 大恢复点只能走 InputStream/OutputStream 流式接口。

2 MiB Android 设备夹具验证单次输入读取请求没有超过 64 KiB，并完成逐字节往返。正式多 GiB 数据、磁盘写满和中档物理机性能仍是发布门禁。

## 8. 删除与失败关闭

删除顺序为：

1. 关闭并清零该 artifact 的现存 lease；
2. 删除独立 Keystore key；
3. 删除 `.zjaf` 及 AtomicFile 备份。

即使进程在第 2、3 步之间中断，遗留的也只是失去可用 key 的密文。密钥缺失、头损坏、类型不匹配和内容认证失败都不会生成替代 key，也不会用空内容覆盖旧记录。

## 9. 测试结果

新增 JVM 格式测试 4 项：

1. 多块往返且单次输入请求不超过 64 KiB；
2. 空 artifact 仍必须具有认证尾；
3. 密文篡改和截断失败；
4. 元数据篡改和尾随字节失败。

新增 Android 专项测试 6 项：

1. 草稿创建/换版加密、输入清零、旧 lease 清零；
2. 旧修订拒绝和写入中断回滚；
3. 2 MiB 恢复点有界流式往返、文件无明文；
4. 类型错误、密文篡改和 Keystore key 缺失失败关闭；
5. App 锁定清零 lease 并阻止内容/元数据访问；
6. descriptor 列表不含正文，删除同时移除文件和 Keystore key。

全项目最终回归：

- JVM 单元测试：103 项，0 失败、0 错误、0 跳过；
- Android 35 x86_64 模拟器测试：55 项，0 失败、0 错误、0 跳过；
- 完整离线构建和 Debug APK 组装通过；
- 源码与 7 个 APK 的 secret 扫描通过；
- 正式数据库主库/WAL/SHM 和草稿/恢复点文件的测试 canary 扫描均为 0 命中。

模拟器控制台仍会出现无害的 `Failed to start Emulator console for 5554` 提示，但 adb 设备在线、55 项测试全部实际执行并成功，不能把该提示误判为测试跳过。
