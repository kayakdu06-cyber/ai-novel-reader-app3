## 2. 来源语义复评与收口

复评发现旧文档中存在一个严重矛盾：阶段顺序把 `EXTRACT_MEMORY` 放在最终提交之前，但部分文字又要求“只从已提交章节提取”。若照字面实现，会在一致性检查/修订前提前发布正文，或者在正文被修订后把旧记忆留在数据库。

现统一为两种合法来源：

1. 正常生成链：正文完成续接后冻结，预分配最终 `ChapterVersionId`，提取结果绑定该 ID 和正文 SHA-256。它仍是候选证据；检查或修订改变正文后必须重新提取，只有与最终正文 hash 一致的结果才能在 TASK-059 原子提交。
2. 记忆重建：来源是数据库中的当前正式 `ChapterVersion`。RequestIntent 落库后、Provider 打开前检查一次，提交前再检查一次；用户换版本后旧请求不能联网或落库。

TASK-056 已完整实现第二条路径，并为第一条路径完成通用请求、严格输出契约和持久化 mapper。候选正文的多阶段推进、修订后重提取和正文+派生数据最终原子提交明确留在 TASK-058~059，未伪装为本阶段已完成。

## 3. 已交付能力

### 3.1 `chapter-memory.v1`

- 根对象及所有子对象关闭额外字段，严格回显来源版本 ID、正文 hash、章节 ID 和章节序号。
- 章节摘要包含目标结果、关键事件、决定、关系变化、结尾状态、未解决问题和重要度。
- 人物事件覆盖位置、身体、情绪、目标、知识、关系、持有物、承诺和秘密。
- 事实覆盖世界事件、人物状态、关系、发现、持有物、承诺、秘密和地点。
- 人物事件和事实各最多 128 条；只允许已知实体，关系事件必须指向另一已知实体；重复事件/事实拒绝。
- 章节提取只能声明 `STORY_CANON` 或 `INFERRED`，不能把模型结果升级成 `HARD_CANON` 或保留为 `PLAN_ONLY`。

### 3.2 请求与 Provider 前门禁

- 请求固定零温度、流式结构化输出、精确 schema；冻结正文最大 4 MiB，已知实体最多 256。
- 冻结正文、实体名称和状态都按敏感 Provider 内容处理；默认对象字符串只显示计数和枚举，不显示正文。
- 记忆重建 Job 的 input source 固定当前版本 ID/hash/章节；Provider-open 事务内重查 SQLCipher 当前版本。版本变化时 Provider 调用数为 0。
- Provider 输出还要通过本地严格 UTF-8、JSON、重复键、深度/节点/大小、schema 和跨字段校验，不能只信服务方的结构化输出声明。

### 3.3 映射、提交和重放

- 摘要、人物事件和事实使用稳定 ID；所有行绑定同一来源 `ChapterVersion`。
- 人物事件的故事顺序使用章节百万跨度，避免不同章节序号碰撞。
- 正式版本重建在一个 SQLCipher 事务中写入三类派生数据、最终 Usage、Stage 和 Job；任一步失败全部回滚。
- 提交许可验证受保护 artifact 类型、修订、原始响应 hash 和规范 JSON hash，防止已校验输出与映射结果脱钩。
- 完全相同的成功提交可精确 replay；来源、payload、存储行或输出引用不同都失败关闭。
- 本阶段复用现有 schema v7，没有新增 Room 表、字段或迁移。

### 3.4 格式失败费用修正

端到端测试发现：结构结果无效并准备自动修复时，原 Attempt 的 Usage 会停留在 `PROVISIONAL`。这会让长期自动生成低估已发生费用，并让临时预算记录堆积。

现已将以下动作放入同一数据库事务：

- 标记 Attempt `FORMAT_INVALID`；
- Stage 进入 `RETRY_WAIT` 或 `NEEDS_ACTION`；
- 原 Attempt 的 Provider usage 或诚实的 `UNKNOWN` 记录升级为 `FINAL`。

格式修复仍最多一次，不会因为结算改动增加自动调用次数。
