# 织卷工作报告 50：E4.8 未知结果恢复审计

> 日期：2026-08-02  
> 对应任务：TASK-047  
> 结论：完成并通过双模拟器、全项目离线构建与安全门禁

## 1. 本阶段交付结果

织卷现在能够在进程崩溃、网络超时、流异常或租约到期后，先判断“旧请求究竟还能不能安全处理”，再决定下一步。恢复不会把“本地执行器失联”误解成“服务端没有执行”。

- 本地已有完整响应：只恢复校验或正式提交，不再请求模型；
- 远端请求仍在运行或查询暂时无结论：保留原 Attempt 和临时用量，等待继续对账；
- 提供方明确证明未执行，且本地草稿为空、没有已知用量、发送证据一致：允许自动回到 `READY`；
- 提供方已完成但本地没有可恢复输出：结算已知用量并进入用户确认；
- 查询不支持、超时、异常、仅有 RequestIntent、草稿不可读或证据相互矛盾：统一保守标记结果未知；
- 用户确认只解除重试门禁，不创建请求、不调用 Provider。真正重试仍需新执行器重新检查预算、租约和发送审计。

默认流程继续遵循“尽量少让用户操作”：能安全本地恢复、等待对账或证明未执行时都由系统处理；只有无法证明不会重复生成和重复付费时才要求用户确认。

## 2. 发现并关闭的严重疏漏

### 2.1 仅有 RequestIntent 不能证明请求未发送

此前最危险的窗口是：一次性联网许可已经被执行器 claim，Provider 请求可能已经离开设备，但 `Started` 事件尚未持久化时进程崩溃。数据库此时仍显示 `INTENT_RECORDED`。

如果把它当成“肯定没发出”直接重跑，会造成重复章节和重复费用。现在该状态默认进入未知结果审计；除非提供方用远端请求 ID 明确证明未执行，否则不能自动回队。

### 2.2 查询原请求与再次生成必须是两个接口

恢复协调器只允许调用 `queryRequestRecovery`，不持有也不调用 `generate()`。状态查询有 1–60 秒边界，默认 15 秒；超时或异常只产生“无结论”，不会借错误路径触发新请求。

当前四个内置远程适配器没有被虚构出不存在的查询能力，统一声明 `NOT_SUPPORTED`。未来只有接入可靠官方端点后才可声明 `STATUS_QUERY`。

### 2.3 用户确认不能成为隐藏的发送按钮

确认事务只做一次 `UNKNOWN_RESULT/NEEDS_ACTION → READY` 的原子状态恢复，不创建 Attempt、不预留费用、不联网。两个并发确认最多一个成功；后续执行器必须重新走完整的领取、预算和发送门。

## 3. 恢复决策矩阵

| 本地与远端证据 | 持久结果 | 自动新请求 |
|---|---|---:|
| 成功响应已持久，Stage 停在校验/提交 | 本地恢复 | 否 |
| 原请求运行中 | `RECOVERY_REQUIRED`，保留原 Attempt | 否 |
| 查询无结论 | `RECOVERY_REQUIRED`，稍后对账 | 否 |
| 明确未执行 + 空草稿 + 无已知 usage + 发送证据一致 | 回到 `READY` | 否；仅回队 |
| 明确未执行但已有正文或 usage | `UNKNOWN_RESULT`，用户确认 | 否 |
| 远端完成但本地无输出 | `UNKNOWN_RESULT`，FINAL usage | 否 |
| 查询不支持、仅有意图、草稿损坏或缺失 | `UNKNOWN_RESULT`，用户确认 | 否 |

## 4. 主要实现

### 4.1 纯恢复策略

- 新增 `UnknownResultRecoveryPolicy`，只根据已持久证据输出互斥决定；
- 草稿证据收敛为“可读空、已有内容、缺失/不可读/冲突”；
- Provider 证据收敛为“不支持、无结论、运行中、明确未执行、已完成但本地无输出”；
- “明确未执行”只是必要条件，仍须通过本地草稿、usage 和发送证据交叉验证。

### 4.2 数据库原子恢复入口

- 新增 `GenerationUnknownResultRecoveryRepository`，统一处理到期审计、活动现场标记未知、远端对账和用户确认；
- Attempt、Usage、Stage、Job 与租约在同一 Room/SQLCipher 事务中核对和推进；
- 用户确认、Provider 证明未执行、等待远端和本地结果恢复使用稳定枚举原因，不写自由文本；
- 通用 Stage 状态入口拒绝恢复专用事件，通用 Job `ISSUE_RESOLVED` 不能绕过稳定恢复原因；
- 没有新增 schema 或恢复表，事实继续由现有 Attempt、Usage、Stage、Job 和加密草稿共同表达。

### 4.3 执行器异常结算

- 受控流式执行器遇到异常时先尽力刷新加密草稿，再原子标记未知结果，然后才向上抛出；
- 流缺少合法终态或 Provider 明确返回 `RESULT_UNKNOWN` 时，同样先完成持久结算；
- 结算后父 Job/Stage 门禁会拒绝迟到的 Started、正文或完成回调，旧执行器不能复活任务。

### 4.4 用量保护

- 进入用户确认时 Usage 置为 FINAL，但保留已有最高可信证据；完全未知仍为 `NULL`，不写 0；
- 原请求仍在运行或查询无结论时保留 PROVISIONAL，允许后续远端证据继续对账；
- 提供方报告最终用量时可按既有单向规则升级；
- 即使提供方证明未执行并安全回队，旧 Attempt 与 UNKNOWN FINAL 审计记录也不会被删除。
