# 织卷工作汇报 18：M1.7 Android 系统备份排除

> 日期：2026-08-01  
> 对应：TASK-016  
> 结论：系统备份关闭与全域排除已经实现；API 35 与 API 30 运行时验收均已通过（API 30 结果见文末补充验证）

## 1. 为什么加密文件仍需要排除系统备份

织卷的小说、草稿、恢复点和 API secret 已经加密，但仍不能允许 Android 系统自动搬运这些文件：

- Keystore key 通常不可迁移，搬走密文只会得到无法打开的残留数据；
- 数据库、WAL/SHM、密钥包装文件和 artifact 必须作为一致集合迁移，系统备份无法保证织卷自己的恢复事务；
- 厂商设备迁移行为与云备份不完全相同，不能只依赖一个总开关；
- 产品已经确定使用“应用内加密备份包”，不需要再维护第二套不可控恢复路径。

因此本任务采用三层防线：清单关闭、Android 12+ 新规则全排除、Android 11 及以下旧规则全排除。

## 2. 本次发现并修复的严重遗漏

原工程已经有：

- `android:allowBackup="false"`；
- `data-extraction-rules.xml`；
- `full-backup-content` 旧规则。

但两份 XML 都只写了：

```xml
<exclude domain="root" path="." />
```

这并不代表“排除整个 App”。Android 把普通文件、数据库、SharedPreferences、外部文件和设备保护存储划分为不同域。只排除 `root` 会漏掉其余域，尤其是正式 SQLCipher 数据库所在的 `database` 域。

本次已把两套规则都补全为九域逐项排除：

- `root`；
- `file`；
- `database`；
- `sharedpref`；
- `external`；
- `device_root`；
- `device_file`；
- `device_database`；
- `device_sharedpref`。

域定义与新旧格式依据 Android 官方的 [Auto Backup 文档](https://developer.android.com/identity/data/autobackup)。

## 3. Android 12 及以上规则

`data_extraction_rules.xml` 同时配置：

- `cloud-backup`：九域全部排除；
- `device-transfer`：九域全部排除；
- 不存在任何 `<include>`；
- cloud backup 额外要求 `disableIfNoEncryptionCapabilities="true"`。

最后一项只是纵深保护；真正的产品策略仍是 `allowBackup=false` 和全域排除。

Android 16 QPR2 开始支持声明跨平台传输，但它需要显式 `cross-platform-transfer`、目标平台和 iOS 身份参数。织卷没有 iOS 对端，也没有声明该节，因此不启用这条路径。

## 4. Android 11 及以下规则

`backup_rules.xml` 使用 `full-backup-content` 格式：

- 同样逐项排除九个域；
- 不存在任何 `<include>`；
- 主清单继续通过 `android:fullBackupContent="@xml/backup_rules"` 引用。

Android 官方明确说明：target Android 12+ 的 App 仍应保留旧格式规则，以支持 Android 11 及以下设备；新系统使用 `dataExtractionRules` 时会忽略旧属性。参考 [Android 12 备份行为变更](https://developer.android.com/about/versions/12/behavior-changes-12)。

## 5. 防止构建变体覆盖安全设置

新增 `verify-backup-exclusions.ps1`，并接入日常 `verify-build.ps1`。每次完整验证都会检查：

- 源码主清单；
- Debug 最终合并清单；
- Release 最终合并清单；
- 三者都必须保留 `allowBackup=false`；
- 三者都必须引用新旧规则；
- 新规则两个模式各有且只有九个根级 exclude；
- 旧规则有且只有九个根级 exclude；
- 任意 include、漏域、重复域、未知域或错误路径都会让验证失败。

`verify-build.ps1` 现在显式执行 Release 清单合并任务，避免只检查 Debug 后错误地认为 Release 也安全。

## 6. 安装包设备测试

新增 3 项 API 35 Android 测试：

1. 安装后 `ApplicationInfo.FLAG_ALLOW_BACKUP=0`，且没有自定义 BackupAgent；
2. 从安装 APK 的资源中解析 Android 12+ 规则，确认 cloud/device 两个模式都完整排除九域且无 include；
3. 从安装 APK 的资源中解析旧规则，确认完整排除九域且无 include。

另外新增设备脚本直接请求 Android Backup Manager：

```text
DEVICE_BACKUP_POLICY_OK
PACKAGE=app.zhijuan.reader.debug
BACKUP_MANAGER_RESULT=Backup is not allowed
```

脚本在测试卸载目标 App 后会从 D 盘 Debug APK 自动重新安装，再执行系统检查，不依赖手工预装状态。

## 7. 新旧系统验收的准确边界

当前本机只有 API 35 x86_64 可启动镜像，因此：

- API 35 安装包资源、清单标志和 Backup Manager 实际拒绝：已通过；
- Android 11 旧 XML 的官方格式、AAPT 打包、Debug/Release 合并清单引用：已通过；
- API 30 系统真正选择旧规则并拒绝备份：已在后续补充验证中通过。

为关闭这一缺口，本阶段尝试下载：

1. API 30 Google APIs x86_64 镜像；

当时两次操作均因下载阶段长时间无输出而主动停止，且没有修改项目或现有 API 35 设备。随后只读复查发现 AOSP API 30 镜像文件已经完整落在项目统一工具目录；后续验证结果见文末补充，不再保留该发布门禁。

## 9. 对用户数据的实际影响

- Android 云备份不会承担织卷恢复；
- Android 设备迁移不会复制织卷小说或连接数据；
- 用户换机时需要使用织卷后续提供的应用内加密备份包；
- API 密钥默认不进入该加密备份，换机后需要重新输入；
- 这会牺牲系统“一键搬家”，但避免密钥失效、部分文件迁移和不一致恢复造成更难理解的数据损坏。
