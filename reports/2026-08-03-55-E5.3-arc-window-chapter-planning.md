# 织卷工作汇报 55：分卷与窗口式分章规划

> 日期：2026-08-03  
> 对应任务：TASK-052 / E5.3  
> 结论：完成

## 1. 本阶段结果

织卷现在不会因为用户选择 300 章或 10,000 章，就要求模型一次输出几百或上万个逐章计划。

本地先固定一个有限范围：

- 当前卷/故事弧最多 40 章；
- 当前逐章摘要窗口最多 8 章；
- 当前计划只剩 3 章时才需要补下一窗；
- 临近总纲节拍或全书结尾时自动缩短；
- 下一窗只能从上一窗结束章 + 1 开始。

模型只负责填写这个已冻结范围内的计划内容，没有扩大窗口、跳章、重叠或提前结束全书的权限。

## 2. 交付内容

### 2.1 本地窗口策略

新增 `zhijuan.arc-window-policy.v1`：

- 对 10,000 章长篇，首次仍只选择第 1–8 章；
- 一个卷最多第 1–40 章，并受当前 master-outline beat 结尾约束；
- 活动卷覆盖下一章时沿用同一卷，只推进 8 章窗口；
- 到全书末章时 `nextWindowStartChapter` 必须为空；
- 补窗阈值是纯本地判断，不需要模型请求，也不增加用户选项。

### 2.2 `arc-plan.v1` 严格结果

结果同时包含：

- 已提交全书总纲 hash；
- 当前父 outline revision hash；
- 目标总章数；
- 当前卷的范围、核心问题、进入/退出状态、里程碑和连续性约束；
- 当前 1–8 章的目标、冲突、转折、结果、钩子和状态承接；
- 精确的下一窗口起始章。

Provider JSON Schema 明确 `maxItems=8` 且所有嵌套对象关闭未知字段。本地再严格检查 UTF-8、重复键、字段/类型/长度/数量、卷与窗口上限、章节连续序列、所有 hash 和冻结选择。

### 2.3 窗口 Job

- 每个窗口是独立 `CONTINUE_BOOK` Job，只含一个 `BUILD_ARC_PLAN / OUTLINE` Stage。
- Job 冻结 Prompt Bundle 版本、总纲 revision/hash、父 revision/hash、总章数、总纲节拍、卷范围、窗口范围和下一窗口指针。
- 相同输入产生相同 input hash/idempotency key；推进到下一窗后必须变化。
- 下一窗口不是运行中动态追加的 Stage，避免崩溃后无法解释“它是什么时候出现的”。

### 2.4 不可变窗口修订

每个成功窗口建立一个新的 outline revision：

- 1 个 BOOK 根节点；
- 1 个当前 ARC 节点；
- 1–8 个当前窗口 CHAPTER 节点。

旧窗口通过 parent revision 链保留，当前 head 只前移。第二窗不会复制第一窗的节点，也不会把全书章节都复制进每个新修订，因此长期存储随窗口数量线性增长，而不是平方增长。

### 2.5 原子提交

提交事务复核：

- 严格校验 permit 与加密 artifact revision/hash；
- 最新成功 Attempt、Usage、Stage、Job、Book、Prompt Bundle 和活动租约；
- Job 冻结的 inputSources；
- master outline revision/hash；
- parent revision/hash 是否仍是当前 head；
- revision 编号、BOOK/ARC/CHAPTER 节点层级、章节连续性和每个节点 hash。

任一条件变化都会整笔回滚。精确重放只读取既有 revision 和节点，不重复插入或重复结算 Usage。

## 3. 关键架构判断

### 3.1 没有把 `BUILD_CHAPTER_PLAN` 改成批量章节阶段

冻结的 Prompt Bundle 已把 `BUILD_CHAPTER_PLAN` 定义为“当前单章的详细场景计划”。TASK-052 的 8 章窗口是更粗粒度的章节摘要，因此放进 `arc-plan.v1 / BUILD_ARC_PLAN`，保留后续单章场景计划的职责边界，避免同一个 phase 同时代表两种不兼容结果。

### 3.2 没有让每个 revision 复制全部历史章节节点

如果每 8 章创建一次 revision，又把所有旧章节节点复制进去，10,000 章会产生约数百万级重复记录。现在每个 revision 只保存本窗，历史由不可变父链追踪，能继续审计来源，也不会出现平方存储。
