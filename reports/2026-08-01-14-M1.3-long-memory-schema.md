# 织卷工作汇报 14：M1.3 长篇记忆与编辑失效链

> 日期：2026-08-01  
> 对应：TASK-012  
> 结论：Bible/Outline/Memory 正式 schema v3、v2→v3 迁移、来源约束和编辑后 stale 失效事务完成

## 1. 本阶段目标

为长篇小说建立不会因章节越多而逐渐失忆、串书或误删正文的本地事实底座，重点保证：

- 故事圣经和大纲可以迭代，但旧版本永远可以追溯；
- 摘要、人物变化、事实、时间线和伏笔都能追到具体章节版本；
- 人物是否明确成年不是一段容易遗漏的提示词，而是数据库可以校验的结构化事实；
- 用户重写前面章节后，旧记忆不会继续参与后文生成；
- 已完成的后续章节只进入待复核状态，不自动删除或覆盖；
- 旧版数据库可以无损升级。

## 2. 新增正式数据结构

schema v3 新增 13 张表：

1. `story_bible_revision`：不可变故事圣经修订；
2. `outline_revision`：不可变大纲修订；
3. `outline_node`：总纲、分卷和章节计划节点；
4. `book_memory_head`：一本书当前采用的圣经和大纲版本；
5. `chapter_summary`：精确绑定章节版本的摘要；
6. `story_entity`：人物、地点、物品、组织和概念；
7. `entity_event`：人物或实体随故事推进发生的状态变化；
8. `canon_fact`：带来源、等级和有效区间的事实；
9. `timeline_event`：故事内事件顺序与约束；
10. `foreshadow_item`：伏笔的计划、埋设、发展和回收；
11. `context_snapshot`：生成某章时实际使用了哪些记忆；
12. `consistency_report`：针对具体章节版本的一致性检查；
13. `aggregate_state_projection`：截至某章的可重建聚合状态。

正式 Room schema 已导出到 `core/database/schemas/app.zhijuan.core.database.ZhijuanDatabase/3.json`。

## 3. 版本化圣经和大纲

- 圣经和大纲修订只能新增，数据库触发器禁止原地修改；
- 每本书的修订号从 1 顺序增加，父修订必须属于同一本书；
- 只有第一版可以没有父修订；
- `BookMemoryHead` 指向当前版本，切换当前版本不破坏历史；
- 大纲节点父子关系由 `(outlineRevisionId, nodeId)` 复合外键约束，不能把旧版节点挂进新版大纲；
- 修订如来自生成阶段，该阶段所属 Job 必须与修订所属书一致。

这使“改设定”成为创建新版本，而不是悄悄覆盖旧事实，后续能够解释某一章当时依据了哪版设定。

## 4. 人物年龄与内容边界

内部模型增加互斥的 `AdultStatus`：

- `CONFIRMED_ADULT`：必须同时保存 `ageYears >= 18`；
- `NOT_ADULT`：必须保存 0～17 的年龄；
- `UNKNOWN`：年龄保持未知，不能被当作已确认成年；
- `NOT_APPLICABLE`：只用于地点、物品等非人物实体，年龄必须为空。

这些组合由数据库插入和更新触发器硬校验，绕开界面直接写库也不能制造矛盾数据。产品界面的内容尺度仍按既定要求采用含蓄命名；这里的明确枚举只服务于内部可靠性和审计。

## 5. 来源和归属保护

本阶段没有只依靠单列外键。数据库会继续核对：

- 章节摘要声明的书和章节序号是否与来源版本一致；
- 人物事件、事实、时间线和伏笔引用的章节版本是否属于同一本书；
- 事实引用的圣经版本是否属于同一本书；
- 上下文快照的目标章节序号是否真实，生成阶段是否属于同一本书；
- 一致性报告和聚合状态的目标章节序号是否与版本真实位置一致；
- 置信度、重要度、schema 版本和伏笔回收窗口是否处于合法范围。

因此不能把另一本书的章节记忆误挂到当前书，也不能靠伪造 `chapterIndex` 破坏失效范围。

## 6. 编辑后的 stale 失效链

`markDerivedDataStaleForReplacedChapter` 在一个事务内执行：

```text
被替换的 ChapterVersion(N)
  ├─ ChapterSummary / EntityEvent / CanonFact / TimelineEvent → STALE
  ├─ 引用该版本的伏笔（来源、实际埋设或实际回收）→ STALE
  ├─ AggregateStateProjection(N..末章) → STALE
  ├─ ContextSnapshot(N+1..末章) → STALE
  ├─ ConsistencyReport(N+1..末章) → STALE
  └─ 后续已有正文的 Chapter → CONSISTENCY_UNKNOWN
```

边界行为：

- 新替换版本自己的有效摘要不会被误伤；
- 后续 `ChapterVersion` 的数量、正文和当前版本引用都保持不变；
- 同一失效事务重复执行时，各项更新数为 0，不反复制造变化；
- 传入错误书 ID 时，在任何写入前失败；
- 伏笔只要“埋设版本”或“回收版本”命中旧章，也会失效。这是本阶段自查时补出的重要漏项，避免只检查创建来源。

## 7. 显式迁移

- 数据库版本从 v2 升到 v3；
- `MIGRATION_2_3` 先补齐章节复合唯一索引，再创建 13 张表及全部索引；
- 迁移末尾安装与新建库相同的保护触发器；
- MigrationTestHelper 从真实导出的 v2 schema 建库并写入旧书，再迁移到 v3；
- 迁移后旧书保持不变，13 张新表、索引、外键和人物年龄触发器均通过 Room 结构验证；
- 未使用破坏性迁移或清库回退。

## 8. 测试结果

新增 Android 数据库测试 6 项（Memory 5 + Migration 1）：

1. 圣经/大纲修订不可变，当前 head 正确推进，跨修订节点父链整体回滚；
2. 成年、未成年、未知和非人物四类合法组合通过，矛盾组合拒绝；
3. 派生记忆不能引用另一书的章节版本；
4. 重写第一章时完整 stale 链生效，新版摘要有效、第二三章正文完整保留、重复执行安全；
5. 错误书 ID 在更改任何派生状态前失败；
6. v2→v3 无损迁移并验证全部新表与保护触发器。

全项目最终回归：

- JVM 单元测试：95 个不重复测试，0 失败、0 错误、0 跳过；
- Android 35 x86_64 模拟器测试：36 个，0 失败、0 错误、0 跳过；
- 其中正式数据库模块 28 个设备测试全部通过；
- 离线构建和 Debug APK 组装通过；
- 源码与 7 个 APK 的 secret/canary 扫描 0 命中。
