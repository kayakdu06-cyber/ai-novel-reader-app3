# 织卷工作汇报 12：M1.1 正式书库 Schema

> 日期：2026-08-01  
> 对应：TASK-010  
> 结论：`Book/BookCreationSnapshot/Chapter/ChapterVersion` 正式加密 Room schema v1、DAO 事务和约束测试完成

## 1. 本阶段目标

把“书、章节和历史版本”从产品文档落成正式数据库事实，优先防止：

- 重生成或人工编辑覆盖旧正文；
- 两个并发任务互相覆盖；
- 崩溃恢复重复提交同一版本；
- 章节误指向另一章的版本；
- 书分支来源丢失或记录错误；
- 删除一本书时由级联关系静默删除核心内容。

本阶段没有提前混入 Job、故事圣经或模板表；它们由 TASK-011～013 分别加入，以便每个 schema 增量都有独立约束与迁移证据。

## 2. 已实现的数据表

### `book_creation_snapshot`

保存创建书时不可变的原始输入、标准化输入、推断来源、题材、呈现配置、模型偏好、schema/提示版本和内容哈希。它不是模板，也不包含连接密钥。

数据库触发器禁止原地更新；需要变化时只能创建新对象，避免“旧书的创建依据被后来设置悄悄改写”。

### `book`

保存书名与来源、状态、篇幅模式和目标、完成章数显示缓存、归档/回收时间以及创建/更新时间。每本书必须且只能引用一个创建快照。

书分支同时记录来源书 ID 与来源章节版本 ID。事务会验证该章节版本确实属于所声明的来源书；只填一半、指错书或自我分支都会拒绝。

### `chapter`

保存书内稳定章序、计划/显示标题、完整章节状态、当前正式版本与一致性状态。`(bookId, chapterIndex)` 唯一。

当前版本不是一个无约束字符串：`(chapterId, currentVersionId)` 复合外键保证它只能指向本章版本，不能把另一章正文挂到当前章。

### `chapter_version`

保存不可变正文、Unicode 字符数、内容哈希、来源、父版本、生成阶段、模型快照与创建时间。`(chapterId, versionNo)` 唯一；父版本同样由复合外键限制在本章内。

数据库触发器禁止 `UPDATE chapter_version`。人工编辑和 AI 重写都只能新增版本，历史正文仍可追溯。

## 3. 原子版本提交

`commitChapterVersion` 在一个数据库事务中完成：

1. 读取当前章节版本；
2. 识别同一生成阶段与内容哈希是否已成功提交；
3. 比较调用方看到的旧版本与数据库当前版本；
4. 创建下一个不可变版本；
5. 用 compare-and-set 切换当前版本；
6. 将章节恢复为可阅读 `READY`；
7. 仅在首个正式版本时增加全书完成章数。

如果章节在生成期间已被人工修改，事务抛出明确的 stale 错误并整体回滚，不留下孤立版本。完全相同的成功生成提交再次执行时返回既有版本，不增加版本号和完成章数。

人工编辑的来源由 `ChapterVersionSource.USER_EDIT` 保存，但保存成功后的章节状态是 `READY`，避免目录把已编辑章节长期当作中间态而隐藏。

## 4. 数据库硬约束

- 创建快照与书一对一；
- 章节序号在书内唯一且必须为正数；
- 版本号在章内唯一且必须为正数；
- 当前版本和父版本不能跨章；
- 正文 Unicode code point 数必须与 `characterCount` 一致；
- 创建快照和章节版本不可原地更新；
- 书分支来源书与来源版本必须成对且归属正确；
- 被分支引用的来源不允许被单边硬删除；
- 核心书、章、版本关系全部禁用级联硬删除。

DAO 保持数据库模块内部可见，其他模块后续只能经过 Repository/用例调用受保护事务，不能直接调用低层 insert 绕过业务约束。

## 6. 实现时发现并修正的问题

### 6.1 Kotlin 与 SQLite 的 emoji 字符计数不同

Kotlin `String.length` 统计 UTF-16 code unit，SQLite `length(text)` 统计 Unicode code point。包含 emoji 时直接对比会把合法正文判为损坏。现统一按 code point 记录，测试夹具覆盖中文加 emoji。

### 6.2 人工编辑后的章节状态不能停在 `EDITED`

状态机中的 `EDITED` 是提交前中间态；若保存事务结束仍保留该状态，而阅读目录只展示 `READY`，用户刚保存的章节反而会消失。现提交成功统一回到 `READY`，版本来源仍准确记录人工编辑。

### 6.3 分支来源不能使用两个独立的 `SET_NULL`

若来源章节版本先删除，只把版本 ID 置空而保留来源书 ID，会形成无法解释的半条来源。现在两项来源引用都使用 `RESTRICT`，正式清理流程必须先处理分支引用，不能静默损坏来源链。
