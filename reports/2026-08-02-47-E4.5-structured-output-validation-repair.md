## 2. 已完成的实现

### 2.1 完整响应证据

正常 `STOP` 终态现在执行以下顺序：

1. 强制 flush 草稿；
2. 停止并等待独立租约心跳退出；
3. 重新核对当前租约、最新 Attempt、唯一草稿引用、artifact 类型、修订和长度；
4. 对草稿原始字节计算 SHA-256；
5. 原子推进 Attempt 为 `SUCCEEDED`、Stage 为 `VALIDATING`；
6. 返回默认字符串脱敏的 `CompletedStreamingResponse` 票据。

把完成落库放到心跳停止之后，关闭了“迟到心跳先写了更大时间、完成记录反而时间倒退”的并发窗口。Attempt 的 `SUCCEEDED` 只表示完整响应已收到并持久化，不表示章节已经正式成功。

### 2.2 严格且有界的本地解析

`StructuredOutputValidator` 在建立 JSON 对象模型之前执行严格 UTF-8 和 JSON 扫描：

- 拒绝空输出、无效 UTF-8、Markdown/解释包装、第二个根值和尾随内容；
- 拒绝重复键，包括 `name` 与 `na\u006de` 这类解码后相同的键；
- 拒绝尾随逗号、非法数字、控制字符和不成对 UTF-16 代理项；
- 默认限制 512 KiB 输入、32 层深度、50,000 节点、每对象 512 成员、每数组 10,000 项、总字符串字符 256 KiB、单个数字 128 字符；
- 根必须是 JSON object；
- 必须包含数值 `schemaVersion`；只接受契约声明的版本；
- 旧版必须经显式迁移并最终产生当前版本，未知未来版和迁移失败均关闭失败；
- 契约问题最多报告 64 项，问题码和路径有界，不携带字段值。

输出超过某个契约的字节上限时，读取层仍会在全局 4 MiB 草稿硬上限内读取完整证据，再由校验器明确判为 `BYTE_LIMIT_EXCEEDED`。这避免了读取异常把 Stage 永久留在 `VALIDATING`。

### 2.3 只允许一次的持久格式修复

第一次格式错误只有同时满足以下条件才可自动修复：

- 错误属于可修复类别；
- 原始输出非空、是合法 UTF-8，且不超过独立的修复源大小上限；
- 同一 Stage 的先前 Attempt 没有 `FORMAT_INVALID`；
- Stage 还有剩余 attempt 名额。

满足时，已收到响应的 Attempt 保持 `SUCCEEDED` 事实，同时持久写入 `standardErrorCode=FORMAT_INVALID`，Stage 进入 `RETRY_WAIT`。新的 RequestIntent 只能把这个明确格式无效的 Attempt 作为重试父节点。

修复次数从数据库中同一 Stage 的 Attempt 链计算，不使用内存布尔值。因此 App 被杀、重启或换执行器后，也不会再次获得“第一次修复”资格。

第二次格式失败、不可修复错误或 attempt 名额耗尽时，Stage 进入 `NEEDS_ACTION`。系统不会循环请求、正则猜值或把错误状态写入故事记忆。

### 2.4 修复请求隔离

`StructuredOutputRepairRequestFactory` 只构造两层提示：

1. 固定的阶段修复契约；
2. JSON 数据信封：schema ID/版本、有界问题码/路径、作为 JSON 字符串的无效输出。

它不会重放原始创作提示，明确把无效输出中的任何指令都当作数据，温度固定为 0，并继续使用 Provider 的结构化 schema。公开 `toString()` 只显示层数、参数和“有结构化 schema”，不显示无效正文。

### 2.5 正式章节隔离

合法输出目前只推进 Stage：

```text
VALIDATING → COMMITTING
```

TASK-044 不创建、不切换 `ChapterVersion`，也不修改阅读目录。正文、摘要/记忆派生任务、Usage、下一阶段和阅读可见状态必须由 TASK-045 的唯一事务共同提交。

`LENGTH`、工具终态、取消、拒绝、EOF 和未知结果也不会冒充正常结构成功；它们继续由 TASK-046、TASK-047 和 TASK-055 的专用路径处理。

## 3. 二次评审发现并关闭的问题

### 3.1 格式无效父 Attempt 被重试入口拒绝

初版已经把第一次格式错误持久写为 `FORMAT_INVALID`，但通用 RequestIntent 入口只允许 `FAILED_RETRYABLE` 或 `UNKNOWN_RESULT` 作为父 Attempt，导致修复计划无法创建第二个真实 Attempt。

最终规则增加唯一例外：`SUCCEEDED + FORMAT_INVALID` 可以成为格式修复父节点；普通 `SUCCEEDED` 仍不允许被当成重试来源。

### 3.2 待校验草稿被误分类为失败保留

初版草稿恢复分类把所有 Attempt `SUCCEEDED` 且 Stage 尚未 `SUCCEEDED` 的情况都当作“失败保留”。这会把 `VALIDATING/COMMITTING` 的有效草稿放入错误的清理语义。

最终改为：

- Stage `VALIDATING/COMMITTING` 且 Attempt 无错误：`RECOVERY_REQUIRED`；
- Stage 正式 `SUCCEEDED`：成功保留 24 小时；
- `FORMAT_INVALID` 或明确失败状态：未成功保留 7 天。

### 3.3 心跳与完成时间竞争

初版在心跳协程仍运行时记录完成；测试时迟到心跳可能先推进 Stage 时间，完成写入随后被单调时间门禁拒绝。

最终先取消并等待心跳，再取得完成时间并写入响应证据，保留严格单调门禁。

### 3.4 超契约大小在读取层提前失败

初版按契约上限读取受保护文件；超过上限时存储层先抛错，校验器不能产生不可修复报告，Stage 可能停在 `VALIDATING`。

最终在全局 4 MiB 安全上限内按实际完整响应大小读取，再交给契约判定。新增双 AVD 专项证明超限结果进入 `NEEDS_ACTION`，不会卡死或发起修复。
