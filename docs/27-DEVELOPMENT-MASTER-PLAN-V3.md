# 织卷开发总规划 V3

> 状态：当前权威开发路线
> 生效日期：2026-08-11
> 适用项目：D:\gptuser\projects\ai-novel-reader-app3
> 目标：先交付可在手机上亲手验证的 3–5 章真实生成与阅读闭环，再扩展成长篇可靠产品

## 1. 本文解决什么问题

织卷已经拥有大量可靠性底层，但“代码很多”和“用户能用”不是同一件事。当前最严重的偏差不是缺少数据库、加密或一致性算法，而是这些能力还没有通过一个完整产品流程连接起来。

从本文生效起，开发顺序改为：

1. 固定组合式小说的通用语义和创作策略包；
2. 完成一个普通章节从计划到提交的总调度闭环；
3. 用 Fake Provider 连续生成并阅读 3–5 章；
4. 接入 DeepSeek V4 Flash，用最高敏感度样本验证小说逻辑、内容合同和速度；
5. 用户在真实手机上亲手验收；
6. 再补模板、阅读体验、长篇压力和备份发布。

不得再以“新增一个底层仓库、校验器或审计器”单独宣称产品里程碑完成。每个阶段都必须产生用户可见结果或完整链路证据。

## 3. 产品硬边界

### 3.1 必须保留

- 单人、本地优先 Android App。
- 无账号、会员、支付、社区、商城和管理后台。
- 用户只需提供一句故事设想；高级资料默认折叠且可空。
- 首次连接 API 后尽量不再要求用户介入。
- 短篇不少于 80 章；中篇不少于 300 章；长篇由用户填写 301–10,000 章。
- 题材、背景、关系、故事机制、叙事结构和文风均允许用户自由描述并任意组合，不设封闭类型清单；本文出现的修仙、恋爱、系统等名称都只是例子，不是白名单或支持上限。
- 已完成章节立即可读，后续章节继续在后台生成。
- 模板可从旧书提取并重开，保留来源、分类和版本，不复制正文和密钥。
- API、中转站、小说、模板、设置和用量台账保存在本地。
- 外部服务拒绝、限流或能力不足时如实显示，不做绕过。
- 所有涉及亲密呈现的角色必须明确为虚构成年人；年龄缺失或不确定时失败关闭。
- 屏幕锁、生物识别、FLAG_SECURE 和最近任务遮挡已经取消，不得擅自恢复。

### 3.2 第一份可验证版本暂不要求

- 完整 80 章或 300 章长跑。
- 所有 Provider 的真实付费测试。
- 完整多看级阅读设置、字体和翻页动画。
- 手动加密备份 UI。
- 全量模板管理和高级分类筛选。
- 用户编辑后从任意历史章节大规模重建。

这些不是删除，而是放到用户先验证核心价值之后。

### 3.3 开发执行硬约束

#### 严格模块边界

- VS-1 沿用现有十模块，不新增模块。
- 每个任务必须先声明主模块和允许修改的配套模块；未列出的模块禁止修改。
- `:core` 只承载纯 Kotlin 公共模型和跨模块契约。
- `:data` 只承载存储、安全、诊断和已有持久事务，不新增 UI 或 Provider 逻辑。
- `:provider` 只承载协议、transport、模型能力和 Fake。
- 业务调度放在 `:feature:generation`；连接、创建、阅读、书架和模板各自留在对应 feature。
- `:app` 只做导航、依赖组装和最小状态转交，不写业务规则。
- feature 不新增直接实现依赖；唯一既有例外仍是 `:feature:template → :feature:creation`。
- 跨模块功能按模块分批开发，每个模块批次独立审查、提交和推送；不得用 sourceSets、复制类或通用 service locator 绕过依赖边界。

#### 不主动扩展

- 只实现当前可验证闭环直接需要的能力。
- “以后可能有用”不能成为新增抽象、表、设置、Provider、插件或 UI 的理由。
- 只有缺少某项会直接导致崩溃、数据污染、重复收费、安全问题、无法恢复或已确认严重 bug，才允许扩展当前任务。
- 扩展前必须写出具体故障链和最小修复；能在现有结构内修复时不新造系统。
- 发现非阻塞改进只记入候选清单，不顺手实现。

#### 精简测试

- 每个测试必须对应一个具体风险；没有独立风险的重复用例不新增。
- 单模块纯逻辑只跑该模块相关测试和编译。
- 跨模块合同只补一个真实交接集成用例，并运行模块边界检查。
- 数据库迁移、密钥、预算、Provider-open 和 runner 原子性属于高风险，运行专项回归。
- assembleDebug 只在可安装/可导航切片变化时运行；全量 test、Release/R8、双 Android API 和 APK 扫描留给里程碑、发布或对应平台风险变化。
- 文档任务不构建 App。

### 4.1 工程规模

- 10 个 Gradle 模块。

- Kotlin 约 60,100 行，其中生产代码约 53,881 行，测试代码约 5,803 行；其余主要是 debug 工具。

- SQLCipher 正式库、Keystore 密钥、加密流式草稿。

- 多协议 Provider 适配、统一错误和重试证据。
- Prompt Bundle v1、故事圣经、全书总纲、分卷窗口和章前上下文。
- 章节正文流、截断续接、记忆、时间线、伏笔、一致性、修订和原子提交。
- 中文 FTS 召回、编辑后失效和派生状态重建。
- Fake Provider、时序记录、Foreground Service 和 WorkManager。

### 4.4 不能误报为已完成的能力

- 普通 chapter-plan 只完成到 exact-token 请求准备，仍未注册到总 runner。
- initial draft 缺少完整的生产来源合同、执行和提交接线。
- 当前 registry 只安全开放有限本地 route，不等于全阶段 dispatcher。
- ReaderSessionCoordinator、LibraryCatalog、TemplateCatalog 存在代码但没有产品入口。
- 费用确认页明确显示未调用模型。
- 尚无一次 App 内 DeepSeek V4 Flash 的端到端生成证据。

## 5. 偏差诊断

### 5.1 为什么开发量大

早期规划按“正式长篇系统”直接建设了加密、预算、恢复、编辑重建和多 Provider 等高成本能力。它们有价值，但多个底层任务完成后没有立即接到可见用户流程，导致架构深度超过产品闭环深度。

### 5.2 最大风险

1. 继续扩展底层，用户仍无法验证小说逻辑、敏感内容合同和真实速度。
2. 把快捷预设或文档示例误当成题材白名单，导致自由输入被丢弃、改写或拒绝；或将所有题材规则硬塞进 Prompt，造成组合污染。
3. 每章调用过多模型阶段，速度和费用不可接受。
4. 全书一次性骨架过大，模型难产、超时或产生虚假细节。
5. 为追求零错误堆叠上下文，让正文模型承担过重输入。
6. 真实 API 测试拖到最后，才发现 schema、流式协议、小说逻辑或敏感场景合同不适配。
7. 直接安装第三方 skill 到 App，带来不可审计提示、脚本和许可证风险。

## 6. 新的目标架构

### 6.1 三层职责

| 层 | 负责什么 | 不负责什么 |
|---|---|---|
| 本地确定性层 | 状态、来源、版本、预算、幂等、硬规则、索引和提交 | 不凭空理解文学含义 |
| 创作策略层 | 选择本章需要的写作规则、任务卡、风格和能力片段 | 不直接联网，不执行第三方脚本 |
| 模型语义层 | 规划、正文和复杂语义分析 | 不作为唯一事实源，不直接改权威状态 |

### 6.2 题材输入开放，状态能力按需

用户输入的题材、关系、机制、结构和文风是开放文本，可以组合现有预设没有列出的内容。原始描述和自由标签必须进入创建快照与后续规划，不得因为没有命中预设而被丢弃、拒绝或静默改写成默认题材。

BookCapabilityManifest 不是“允许写哪些小说”的清单，只记录这本书可能需要哪些结构化、长期状态规则；每章再生成 ChapterCapabilityActivation。只有需要确定性保持数值、归属、阶段、承诺或其他跨章不变量的机制，才值得增加专用适配器。下列名称仅是首个纵向切片的状态适配器示例：

- cultivation：修炼体系与境界；
- romance：关系进展和情感承诺；
- progression-system：任务、积分、等级和奖励；
- intimacy-continuity：相关场景的过程与余波；
- mystery：线索、误导和揭示；
- item-progression：道具归属、状态和成长；
- politics：阵营、利益和信息边界。

没有专用适配器的自由题材仍由通用叙事、人物连续性、叙事义务和证据外壳正常处理，不能因此拒绝生成；缺少的只是该机制的额外确定性校验。没有激活的专用能力不进入本章 Prompt，也不占用相关状态字段。一本书可以同时启用多项能力，但每章只携带当前真正相关的最小集合。

开放题材输入不等于开放可执行扩展：首版仍不提供动态 capability、插件或运行时 skill 安装。新增专用适配器必须由真实的跨章可靠性缺陷驱动，不能按题材数量预建。

### 6.3 正常章节远程调用预算

VS-1 初始闭环允许每个正常章最多三次主要远程调用：

1. 章节计划：生成本章任务、场景和预期状态变化；
2. 流式正文：尽快输出完整、非乱码的正文；
3. 章后合并分析：一次返回摘要、事实、人物/关系/道具/系统状态、伏笔和一致性结论。

仅严重问题时增加一次修订，修订后再进行必要的合并分析；所有正式写入和门禁仍在本地完成。

两次调用是后续优化目标，不在未验证前伪装成已实现：R3 基准后比较“独立章节计划”与“从 arc-window v2 章节点本地物化计划”。若独立计划没有带来可测的小说逻辑收益，就收敛为“正文 + 合并分析”两次；若小说逻辑收益明显，可以保留三次，但仍必须满足整章速度上限。无论采用哪种路线，都不得把现有多个分析 Stage 逐一变成额外远程调用。

### 6.4 滚动规划代替全书一次性细纲

- 全书只生成稳定的主题、核心冲突、主要人物和结局方向。
- 分卷规划覆盖较粗目标。
- 逐章只规划 1–8 章有限窗口。
- 剩余 3 章时补窗。
- 新窗口必须消费已发生事实、未完成义务和能力状态。
- 不要求模型一次写完 80、300 或上千章的逐章大纲。

## 7. 开发流程重排

### 阶段 A：冻结最小语义，不联网

交付：

- WritingPolicyPack 最小内置合同、版本和冲突规则；来源/许可证只保存在开发文档，不建设运行时管理系统；
- BookCapabilityManifest 与 ChapterCapabilityActivation；
- 只覆盖首个验证样本实际使用字段的 NarrativeObligation 与 StoryStateDelta；
- chapter-plan v2 和 chapter-post-analysis v1 合同；
- 优先复用现有不可变 Stage/Context JSON；只有现有存储不能保证恢复和原子提交时才新增 migration。

闸门：相关模块的最小 JVM 测试通过；只有实际新增 migration 才跑 Room 迁移专项；未激活能力不进入 Prompt；不调用真实 Provider。

### 阶段 B：单章 Fake 闭环

交付：

- 从费用确认页真正创建 Job 并启动 total runner；
- chapter plan → context → draft → post-analysis → commit 全链；
- Fake Provider 流式首段；
- App 可看到生成状态和最终第一章。

闸门：杀进程、暂停、继续、停止、重复启动、预算拒绝和提交重放全部通过；不出现双章或重复收费事实。

### 阶段 C：3–5 章 Fake 纵切

交付：

- 连续自动推进 3–5 章；
- 书架显示进度；
- 目录显示已完成、生成中和待生成；
- 已完成章节立即阅读；
- 后台继续生成；
- 当前章失败不损坏前章。

闸门：设备上从创建到阅读无开发者操作；用户可暂停和继续。

### 阶段 D：DeepSeek V4 Flash 真实验证

交付：

- 真实 OpenAI Chat Compatible 流式请求；
- 一个最小结构合同 smoke 和一个 3–5 章混合题材连续样例；不再为每种题材单独建重复样本；
- 小说逻辑、最高敏感度场景合同、延迟、token、费用和拒绝报告；
- 按事实修订 schema、Prompt 和模型参数。

闸门：用户授权的真实 API；密钥不进仓库和日志；第一可读段、正文和最终提交满足 31 号文档阈值。

### 阶段 E：亲手验证 APK

交付：

- 可安装 Debug/内部 APK；
- 用户在已连接测试机上完成创建、开始、阅读、暂停和恢复；
- 明确收集“计划和因果是否成立、剧情是否重复、状态是否可信、敏感场景合同是否完成、速度是否可接受”五类反馈；不采集文笔分数。

闸门：29 号文档所有 P0 验收通过。若失败，先修核心闭环，不扩展外围功能。

### 阶段 F：个人可靠版

交付：

- 模板提取、来源、分类、版本和三步重开；
- 阅读器目录、主题、字号、进度和生成状态融合；
- 20 章真实连续生成；
- 编辑后局部失效与重建；
- 手动备份与恢复；
- 物理设备和发布构建验收。

### 阶段 G：按证据触发的长篇稳定版

交付：

- 先做 20 章真实连续样本；只有它暴露不了长期漂移或准备 1.0 发布时，才升级到 80 章真实/分段样本和 300 章状态模拟；
- 状态漂移、重复剧情、关键义务丢失和费用趋势报告；
- 只对报告中实际失败的窗口、压缩或召回阈值调优；
- 1.0 候选 APK。

## 8. 每个任务的标准流程

1. 读取当前权威文档和任务包。
2. 确认 Git 根目录正好是 app3。
3. 记录任务开始前 Git 状态，不覆盖用户已有修改。
4. 声明主模块、允许配套模块、禁止模块和具体依赖方向。
5. 边界明确的机械实现可交给 DeepSeek，使用最高推理强度和足够超时。
6. DeepSeek 的输出只有形成真实文件差异才算代码贡献。
7. Sol 审查全部差异，删除越界改动和未经证明的扩展。
8. 按 3.3 的风险等级只运行最小必要测试；不得把全量门禁当成每个小任务的固定仪式。
9. 更新任务文档、工作报告和 CURRENT-CONTEXT。
10. 单独提交并推送 Git；未通过的中间状态不得标完成。

## 9. 速度与可靠性闸门

### 9.1 用户体验硬线

| 指标 | 推荐目标 | 可验证版本上限 |
|---|---:|---:|
| 本地点击开始到 Provider 打开 P95 | ≤2 秒 | ≤3 秒 |
| 第一可读段 P50 | ≤10 秒 | ≤10 秒 |
| 第一可读段 P95 | ≤20 秒 | ≤25 秒 |
| 3,000–5,000 中文字正文 P95 | ≤180 秒 | ≤300 秒 |
| 正式提交 P95 | ≤240 秒 | ≤360 秒 |
| 单章超过 5 分钟 | 显示慢服务状态 | 必须可暂停/取消 |
| 单章超过 10 分钟 | 故障 | 阻断发布 |

测试工具可以无限等待 Provider 最终返回以收集证据，但 App 产品状态不能无限沉默等待；两者不得混淆。

VS-1 的 3–5 章只报告逐章值、中位数和最慢值，不用少量样本声称 P95；推荐模型的 P50/P95 至少在后续 20 章证据后计算。

### 9.2 小说逻辑硬线

- 不重复上一章的核心事件作为新剧情。
- 本章必须推进至少一个明确目标或制造可追踪后果。
- 已发生的关键关系、承诺、伤势、道具归属、系统等级和伏笔不得无证据回退。
- 计划义务必须完成、延期或明确取消，不能凭空消失。
- 不把模型分析直接写成权威状态；先校验来源和允许的状态转移。
- 发现严重矛盾时不得正式提交。

## 10. 工期估算

以下为有效开发工时，不是自然周承诺，也不包含外部服务长时间故障：

| 目标 | 预计工时 | 结果 |
|---|---:|---|
| 最小语义合同 + 单章 Fake 闭环 | 50–82 小时 | App 内可生成并提交第一章 |
| 3–5 章 Fake + 产品接线 + 真实 API + 手机验收 | 再 32–50 小时 | 第一份可亲手验证 APK |
| 模板、阅读完善、20 章可靠性和备份 | 再 44–80 小时 | 可日常试用的个人版本 |
| 80 章/300 章扩展验证 | 仅在 20 章证据或发布闸门要求时另估 | 1.0 长篇证据 |

按删去运行时 skill 管理、无条件 migration、重复题材样本和每任务全量门禁后的范围，从当前状态到“可亲手验证”约 82–132 个有效工程小时。这个数字仍包含持久调度、真实 API、最小 UI 接线和高风险恢复验收；后续不得再通过主动扩展把它拉回旧规模。

## 11. 暂停精简的裁决

现在不以行数为目标做大规模删除。原因：

- 60,000 行中包含大量已经验证的安全、恢复和数据约束；
- 删除不能直接让第一章跑起来；
- 在总链未连接前很难判断哪些代码真是死代码。

允许的精简时点：

1. 3–5 章 Fake 闭环后，用真实调用图确认未使用路径；
2. DeepSeek 实测后，确认某些 Provider 或阶段对 1.0 无价值；
3. 20 章稳定后，删除被新合并分析正式替代且无恢复用途的旧远程路径。

每次精简必须有调用证据、编译测试和数据库兼容结论，不按“看起来重复”删除。

## 12. 成功定义

第一成功不是“全书系统架构完整”，而是用户可以在手机上：

1. 选择或新增 DeepSeek 连接；
2. 输入一句故事设想；
3. 确认章节规模、目的地和预算；
4. 点击一次开始；
5. 在 25 秒内通常看到第一段；
6. 阅读第一章时第二章继续生成；
7. 在书架和目录看到可信进度；
8. 暂停、退出、重启后继续；
9. 连续 3–5 章不重复关键剧情、不丢失关键状态；
10. 获得可理解的速度、费用和失败信息。

做到这十点后，才进入模板、阅读精修和长篇扩展。
