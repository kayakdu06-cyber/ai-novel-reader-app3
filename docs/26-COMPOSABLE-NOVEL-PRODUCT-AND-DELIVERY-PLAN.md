## 1. 本次评审结论

织卷不应被设计成“选择一个固定题材，然后套用一套提示词”的小说生成器。真实小说通常同时包含多个维度，例如修仙世界、系统机制、恋爱关系、特定内容呈现、冒险主线和道具成长。

现有架构的任务恢复、版本、数据来源、预算、Provider 安全、章节记忆和编辑后重建基础仍然有效，不需要推倒重来。当前最缺少的是位于这些基础设施之上的“组合式小说语义层”：它要把用户需要的多种能力组合起来，但只在相关章节启用，所有能力共同使用一份事件和状态事实，不能分别维护互相矛盾的记忆。

后续第一交付目标不是立即完成正式版，而是完成一个可安装、可亲手验证、不是一次性演示壳的纵向验证版本：

- 在 Android 测试机中创建一本组合题材小说；
- 使用真实 DeepSeek V4 Flash API；
- 生成故事基础、短期窗口计划和连续 3～5 章正文；
- 第一段正文流出后即可阅读；
- 能看到本章人物、剧情任务和关键状态的本地记录；
- 能暂停、恢复，并验证不会重复提交章节；
- 能观察一次关系变化、道具变化或系统状态变化如何进入下一章；
- 该验证链沿用正式数据库、runner、Provider、预算和版本边界，后续可继续扩展，不另做一套废弃原型。

## 2. 产品目标

织卷是一款单人、本地优先的 Android AI 小说生成与阅读 App。

用户只需要完成少量操作：

1. 输入简单人物和故事想法；
2. 选择或组合题材、文风、内容呈现和篇幅；
3. 选择已经保存的模型连接；
4. 点击开始；
5. 阅读已经生成的章节，后续章节在后台继续生成。

产品必须满足：

- 短篇至少 80 章，中篇至少 300 章，长篇由用户自定义；
- 不要求用户理解 Prompt、Token、上下文或任务状态机；
- 不做账号、会员、支付、社区和管理后台；
- 小说、连接、密钥、模板和设置保存在本地；
- 支持主流 API 与 OpenAI-compatible 中转站；
- 已完成正文立即可读，后台分析不能长时间阻塞阅读；
- 模板保留来源、分类、版本和复制链，可快速重新生书；
- 阅读体验以沉浸、中文排版和低操作量为核心。

## 3. 产品不是固定题材分类器

### 3.1 书籍能力清单

创建一本书时，系统内部冻结一份 `BookCapabilityManifest`。它不是给用户看的复杂配置表，而是由模板、用户的自然语言和少量选项共同产生。

第一阶段建议支持以下通用能力：

| 能力 | 负责内容 | 是否所有书都启用 |
|---|---|---|
| `CORE_STORY` | 主线、人物、地点、事件、章节目标 | 是 |
| `RELATIONSHIP` | 人物关系、承诺、秘密和关系变化 | 按书启用 |
| `WORLD_PROGRESSION` | 修炼境界、能力成长、世界硬规则 | 按书启用 |
| `SYSTEM_MECHANICS` | 任务、经验、等级、奖励和触发条件 | 按书启用 |
| `ITEM_STATE` | 重要道具、持有、数量、状态和转移 | 按书启用 |
| `MYSTERY_CLUE` | 线索、证词、嫌疑与排除关系 | 后续启用 |
| `RESOURCE_MANAGEMENT` | 经营、资源、势力和组织状态 | 后续启用 |
| `CONTENT_PRESENTATION` | 相关场景的呈现合同和人物门禁 | 按书启用 |

题材只用于提供默认组合。例如“修仙系统恋爱”可以映射为：

```text
CORE_STORY
WORLD_PROGRESSION
SYSTEM_MECHANICS
RELATIONSHIP
CONTENT_PRESENTATION（若用户选择）
```

### 3.2 全书启用与本章激活分离

一本书可以启用多个能力，但每章只能激活真正相关的子集。

例如：

- 普通修炼章只加载世界规则、当前修为和本章人物；
- 感情推进章加载相关人物关系和必要世界事实；
- 系统任务章加载当前任务、触发条件和奖励状态；
- 同时影响关系、系统和修为的关键章加载三个能力，但必须形成清晰因果链。

未激活能力不能进入 Prompt，不能增加远程 Stage，也不能消耗额外 API Token。

## 4. 统一故事语义核心

### 4.1 模型是内容提案者，本地是事实裁决者

API 可以创作和分析，但不能直接修改权威状态。所有模型输出先成为候选，经本地结构、来源、版本和规则验证后，才能成为当前事实。

### 4.2 统一事件，而不是多个模块各记一份

人物关系、系统升级、道具转移和修为突破必须引用同一个章节事件。

一个事件至少包含：

- 事件 ID 和合同版本；
- 来源书籍、章节版本和正文哈希；
- 参与实体；
- 发生前状态；
- 发生后状态；
- 正文证据位置和证据哈希；
- 触发的能力规则；
- 新产生或完成的剧情义务；
- Canon 等级和置信度；
- 当前状态：有效、过期或失败。

示例因果链：

```text
章节事件
  → 人物关系发生变化
  → 满足系统任务条件
  → 本地结算奖励
  → 满足修为变化条件
  → 产生下一章必须处理的后果
```

### 4.3 事实、推断和计划严格分层

- `HARD_CANON`：用户设定和已经确认的世界硬规则；模型不能覆盖。
- `STORY_CANON`：最终正文中有可定位证据的已发生事实。
- `PLAN_ONLY`：尚未执行的章节计划和剧情义务。
- `INFERRED`：模型推断的情绪、动机或关系倾向，不能覆盖事实。

结构正确不代表语义正确。模型提取的证据必须能够在最终正文中定位；找不到证据时不能升级为正式事实。

## 5. 每章的规划和生成流程

### 5.1 分层规划

```text
故事基础与 Story Bible
  → 全书总纲
  → 故事弧/分卷
  → 未来约 8 章的滚动窗口
  → 当前章场景计划
  → 正文
```

不一次细化 80 或 300 章。全书只冻结主线、结局方向和关键里程碑；具体章节采用滚动窗口，避免前期计划在几十章后全部失效。

### 5.2 窗口计划需要提供

- 每章主要目标；
- 冲突、转折、结果和结尾钩子；
- 本章主要人物；
- 本章激活的能力；
- 必须发生的状态变化；
- 必须延续到下一章的状态；
- 到期的剧情义务；
- 新人物或新重要道具的受控引入意图。

此前 Phase 2E5B 设计的相关场景意图应当保留其严格门禁，但在实现前提升为 `CONTENT_PRESENTATION` 能力的小合同，避免以后继续向章节根结构添加每种题材的专用字段。

### 5.3 章前上下文

本地只选择当前章所需信息：

1. 用户和世界硬规则；
2. 当前章计划；
3. 到期且不可裁剪的剧情义务；
4. 上一章最终状态；
5. 当前参与人物、重要道具和机制状态；
6. 与当前目标相关的远期记忆；
7. 最近章节的压缩摘要。

搜索召回只能补充相关历史，不能承担关键剧情义务。关键剧情不能因为搜索漏召回而消失。

### 5.4 正文与后台处理

为了速度，正文应尽快流式展示。正常章节的目标流程是：

1. 一次正文主生成；
2. 正文达到可读条件后立即进入阅读页；
3. 后台进行一次合并的记忆、状态变化、剧情义务和一致性分析；
4. 只有严重问题才进行一次修订；
5. 后台结果完成后更新下一章上下文。

不能为关系、道具、系统和修为分别调用一次 API，否则组合能力越多，单章越慢。

## 6. 剧情重复和关键剧情保护

### 6.1 剧情变化账本

每章除摘要外，还要保存：

- 新获得的信息；
- 已解决的问题；
- 人物决策；
- 关系变化；
- 道具和资源变化；
- 能力或地位变化；
- 新风险；
- 推进或完成的剧情义务；
- 章节开头到结尾的不可逆变化。

下一章计划需要与历史变化比较。相似措辞不是重复，剧情功能和状态变化高度相似且没有新结果，才应进入重复风险检查。

### 6.2 剧情义务账本

关键剧情采用：

```text
PLANNED → DUE → EXECUTED → VERIFIED
```

只有在最终正文中找到有效证据后才能进入 `VERIFIED`。未验证义务必须继续进入后续窗口；到期仍未执行时应修订或重新规划，不能静默跳过。

### 6.3 能够保证和不能保证的边界

可以强约束：

- 关键义务不会无记录消失；
- 旧章节状态不会在编辑后继续生效；
- 已确认道具、人物和规则不会被无理由覆盖；
- 同一事件不会重复结算；
- 未启用能力不会进入请求；
- 结构和状态冲突会在正式提交前暴露。

不能绝对保证：

- 模型每章都具有优秀文学质量；
- 所有语义提取都完全正确；
- 所有相似剧情都能区分为合理呼应或重复；
- 任意模型都能同等服从复杂组合规则。

## 7. 人物、道具和机制状态

### 7.1 人物与关系

关系不能只保存“好感度”。需要保存有证据的关系状态、承诺、秘密、冲突和关键变化。模糊情绪只能作为推断。

### 7.2 道具

现有代码已经有 `ITEM`、`POSSESSION`、道具归属冲突和物品连续性基础，但还缺：

- 新重要道具的正式创建流程；
- 当前持有者或容器投影；
- 数量、消耗、转移、销毁；
- 唯一道具约束；
- 可选的品质、强化和耐久状态。

普通小说只追踪剧情重要道具。库存和数值只在对应能力启用时生效。

### 7.3 系统和修为

等级、经验、奖励和修为变化必须由本地规则结算。模型可以描写触发事件和升级表现，但不能自行决定数值结果。规则含糊时只能生成候选判断，不能伪装成确定事实。

## 8. 规则优先级与冲突

默认优先级：

1. 用户明确设定；
2. 世界硬规则；
3. 已冻结主线和到期剧情义务；
4. 题材机制；
5. 当前人物、道具和关系状态；
6. 本章创作目标；
7. 模型自由发挥。

能力想突破更高层规则，必须存在用户设定中的明确例外。无法解析的冲突必须在调用 API 前失败，不能把矛盾指令一起发送给模型。

## 9. 用户体验

### 9.1 创建流程

用户不直接配置能力依赖。推荐交互是：

1. 输入一句故事想法；
2. 选择几个直观标签或使用模板；
3. App 自动形成能力组合；
4. 用户只看到简短的自然语言确认；
5. 高级规则折叠，需要时才展开。

### 9.2 生成与阅读

- 点击开始后自动规划和生成；
- 第一段流出后即可进入阅读；
- 目录显示生成中、可读、待处理和失败状态；
- 阅读页不显示复杂任务日志；
- 错误只提供少量明确操作：继续、换连接、调整预算或重新生成；
- 后台分析不得打断已经可读的正文。

### 9.3 模板复制

模板必须记录：

- 来源书籍与来源标题快照；
- 根模板和派生链；
- 当前模板版本；
- 题材能力组合及其版本；
- 人物原型、世界规则、文风和内容呈现；
- 用户修改项；
- 哪些运行期内容不应复制，例如旧章节正文和旧任务状态。

## 11. 可亲手验证版本

### 11.1 验证范围

第一版只要求证明产品核心成立，不要求立即完成所有功能：

- 一种代表性的组合模板，例如世界成长＋系统机制＋人物关系，可选内容呈现；
- 2～4 个主要人物；
- 1～3 个重要道具；
- 故事基础、总纲和首个 8 章窗口；
- 使用真实 DeepSeek V4 Flash 连续生成 3～5 章；
- 正文流式显示并可进入阅读；
- 展示简化生成状态；
- 验证至少一次人物关系变化；
- 验证至少一次道具或系统状态变化；
- 验证一个剧情义务从计划到正文证据；
- 暂停、恢复和 App 重启后不重复提交；
- 保留完整本地数据，后续可以继续扩展到正式版本。

### 11.2 可以暂缓

- 80 或 300 章完整长跑；
- 所有题材能力；
- 任意用户自定义规则语言；
- 完整库存、耐久和复杂数值经济；
- 全套阅读主题和动画；
- 发布商店、导入导出和正式迁移支持；
- 模板市场或任何后台功能；
- 极端故障的全部 UI 文案。

### 11.3 验证成功标准

验证版至少满足：

- 用户能在测试机完成创建、开始生成和阅读，不需要开发工具操作数据库；
- 真实 API 生成的 3～5 章具有连续人物和情节；
- 本地记录能够解释每章推进了什么、哪些人物和道具状态发生变化；
- 到期剧情义务没有静默丢失；
- 普通章节不重复提交；
- 重启后可以继续；
- 正文首段在合理时间出现；
- 普通章节不能出现十分钟仍没有可读正文的正常状态；
- 生成失败时提供可理解的恢复入口。

## 12. DeepSeek V4 Flash 真实 API 测试方案

用户已经明确要求：内容效果、真实速度和最终端到端验收必须使用真实 DeepSeek V4 Flash API。后续用户确认开发后，这项要求覆盖此前“App 内真实 Provider 调用为 0”的旧测试限制。

真实 API 不能替代 Fake 和本地测试，两者职责不同：

- Fake/本地测试负责稳定复现断流、超时、重复响应、崩溃、非法 JSON、预算拒绝和数据库回滚；
- 真实 DeepSeek V4 Flash 负责验证真实内容质量、结构服从、首段时间、整章时间、连续生成和多题材理解；
- 一个阶段只有 Fake 通过而没有对应真实内容验证，不能作为最终产品验收；
- 一个阶段只有真实 API 偶然成功而没有确定性失败测试，也不能视为可靠。

### 12.1 测试阶梯

1. **连接冒烟**：最小非敏感请求，验证连接、流式响应和脱敏日志。
2. **合同冒烟**：故事基础、窗口计划和章节计划各少量真实调用，观察严格 JSON 服从率。
3. **单章链**：真实规划、正文和后台分析完整跑通。
4. **3～5 章验证**：作为第一份可安装验证版的核心验收。
5. **20 章稳定性**：暂停、恢复、重启、一次编辑重建、一次模型输出修复。
6. **80 章低干预长跑**：在可靠个人版后进行，不作为第一验证版的前置条件。
7. **组合矩阵**：单能力、两两组合和一个代表性四能力组合。

### 12.2 采集指标

- 首个可见正文时间；
- 整章正文完成时间；
- 正式验收完成时间；
- 每章远程调用次数；
- 输入、输出和推理 Token；
- 自动修订率；
- 结构输出失败率；
- 断流与恢复结果；
- 人物、道具和规则冲突；
- 剧情义务兑现率；
- 剧情功能重复率；
- 每章费用及 20/80 章预计费用。

### 12.3 初始性能目标

这些是验收目标，不是当前已经取得的真实 API 结果：

- 第一段正文：P50 不高于 10 秒，P95 不高于 25 秒；
- 3,000～5,000 汉字普通章节正文：P50 不高于 150 秒，P95 不高于 300 秒；
- 普通章节超过 10 分钟仍无可读正文：判定为故障；
- 正常章节最多一次主正文生成和一次合并后台分析；
- 自动修订只在严重问题时触发；
- 阅读当前章时允许后台继续处理下一章。

最终阈值必须依据真实 DeepSeek V4 Flash 数据修订，不能用 Fake Provider 的数字冒充真实性能。

### 12.4 密钥与安全

- 不把 API Key 写入代码、文档、命令输出、日志或 Git；
- 使用项目已有隔离密钥入口或 App 加密连接存储；
- 真实内容测试采用专用测试书，不使用其他项目数据；
- 原始正文只保存在 App 加密数据和受保护工件中；
- 报告只保存脱敏指标、错误分类和 hash；
- 每轮长跑前明确最大费用和停止条件。

本文档没有调用任何真实 API。

## 14. 时间估算

以下按“有效开发与验证时间”估算，不等同于模型持续等待的自然时钟，也不把用户主动暂停时间计算在内。真实 API 调优存在不确定性，因此使用范围而不是单一日期。

### 14.1 可亲手验证版本

预计：**45～80 个有效开发小时**。

在环境稳定、不中断推进的情况下，大约对应 **7～14 个日历日**。主要工作：

| 工作 | 估算 |
|---|---:|
| 组合能力合同和章节激活 | 8～14 小时 |
| 统一事件、证据和最小剧情义务 | 10～18 小时 |
| chapter-plan 与一章 runner 闭环 | 12～20 小时 |
| 创建、生成状态和阅读最小接线 | 6～10 小时 |
| DeepSeek V4 Flash 真实 3～5 章测试与调优 | 6～12 小时 |
| 安装、恢复和阶段验收 | 3～6 小时 |

这是推荐的下一交付目标。

### 14.2 可靠个人使用版本

在验证版之后还需约 **70～130 个有效开发小时**，累计约 **115～210 小时**。现实日历约 **3～6 周**。

包括：

- 20 章真实稳定性；
- 编辑后自动重建；
- watchdog 和错误恢复；
- 模板复制；
- 费用预估；
- 阅读体验完善；
- 更多组合能力；
- 性能和远程调用次数优化。

### 14.3 长篇可靠验收版本

在可靠个人版后仍需约 **60～120 个有效开发小时**和多轮长跑，累计约 **175～330 小时**。现实日历通常为 **5～9 周**。

这一级别才适合声称：已对 80 章连续生成、300 章规模规划和长时间恢复进行了系统验证。它仍不能保证每章文学质量，但可以对数据、状态、恢复和主要剧情义务提供更强证据。

### 14.4 影响时间的主要变量

- DeepSeek V4 Flash 对严格结构输出的真实服从率；
- 每章实际长度和输出速度；
- 是否频繁触发修订；
- 组合能力是否出现未预见冲突；
- 测试机网络和中转站稳定性；
- 是否要求第一验证版就包含完整模板复制和阅读设置；
- 用户主动暂停和上下文交接次数。

## 15. 风险与负面影响

| 风险 | 影响 | 控制方式 |
|---|---|---|
| 能力组合爆炸 | 测试和维护量增加 | 稳定外层合同、版本化小合同、成对组合测试 |
| Prompt 过重 | 慢、贵、文字机械 | 按章激活、未启用零输入、严格上下文预算 |
| 多模块重复记忆 | 状态矛盾 | 统一事件事实源和本地 reducer |
| 模型语义误判 | 污染本地事实 | 正文证据位置、Canon 分层、冲突保留 |
| 规则冲突 | 模型随机选规则 | 本地优先级和 Provider 前冲突检查 |
| 门禁过严 | 修订率和费用上升 | 只把身份、硬规则、到期义务设为硬约束 |
| 远程阶段过多 | 单章超过速度目标 | 合并后台分析、按需修订、并行非阻塞处理 |
| 旧书解释变化 | 重放不一致 | 能力和合同版本固定，不静默升级 |
| 开发继续底层化 | 用户迟迟无法验证 | 以 3～5 章真实 APK 为下一硬里程碑 |
| 真实 API 偶然成功 | 误判可靠 | Fake 故障测试＋真实内容测试双轨验收 |

## 16. 推荐决策

建议用户确认后采用以下原则开始开发：

1. 不推倒现有可靠性底座；
2. 在 Phase 2E5C 开始前先增加组合能力层；
3. 不追求第一版支持任意题材规则；
4. 用关系、道具、系统和世界成长验证组合架构；
5. 下一硬里程碑是可安装、真实 DeepSeek V4 Flash、连续 3～5 章的验证 APK；
6. 验证版必须沿正式架构，不创建以后丢弃的旁路原型；
7. Fake 测试负责确定性故障，真实 API 负责内容、速度和端到端验收；
8. 验证版通过后，再决定是否立即扩展到可靠个人版和长篇验收版。
